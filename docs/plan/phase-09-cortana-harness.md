# Phase 09 — Cortana tuning harness: Notebook memory, corrections, rules, scriptable hooks, replay tests

## Goal
Jeremy can correct and tune Cortana the way he tunes Claude. Cortana keeps a persistent memory in the same format as Jeremy's Claude
memory: one fact per file with frontmatter, plus an index that loads into context. The memory is shown and editable in a W10M-style
Notebook. Saying "No, I meant…" or tapping Correct turns a mistake into a stored correction. Declarative rules ("when I say the wife,
use Jane"; "before any text after 10 pm, ask me") and scriptable hooks run around every action. Memory, rules and hooks are also plain
files Jeremy can pull, edit and push from his PC over USB. Every correction becomes a replay test that re-runs after any model, prompt
or harness change and is checked deterministically against the corrected action, with no AI grading.

## Scope
**In:**
- Memory store in Jeremy's Claude memory format: one fact per markdown file with `name` / `description` / `type` frontmatter (user, feedback, project, reference), `[[links]]`, and an index file with one line per memory; index loading and relevance recall within the on-device model's context budget
- W10M-style Notebook UI (Cortana's final-release Notebook measured in R7 §3: a flat list page reached from Cortana's ≡ pane, extended per P4 designs): browse, edit, delete memories, corrections and rules; hooks are view / enable / disable only (no script editor)
- Correction capture by voice ("No, I meant…") and a Correct button (P4 design) on every answer or action card
- Declarative rules: condition → allow / ask / block / rewrite parameters / add context; creatable by voice or in the Notebook
- Scriptable hooks with Claude Code-style events: session start (inject context), before prompt, before action (allow / ask / block / modify), after action, on correction. Scripts run in an embedded sandboxed interpreter with a narrow API and no network
- PC file access over USB: a provider that only accepts calls from the adb shell uid and rejects the phase 04 helper's own process (same uid, told apart by pid; see Decisions), plus a small PC script to pull / push / diff memory, rules and hooks
- Replay tests: every correction stores the utterance, the context-provider inputs at that moment and the expected action and parameters (an answer-only correction stores a string / entity assertion on the answer instead); a runner replays all of them (on the phone, triggered from Settings, the PC script, a harness file push, a model download or the first start after an app update) and reports pass/fail per test
- Memory lookups (e.g. nicknames) are also available to phase 03's fixed commands as an ADD to its contact resolution
- Settings page + checklist rows (harness healthy, hook errors, last replay result)

**Out (explicitly):** retraining or fine-tuning model weights; cloud sync; hooks with network access; voice-created scripts (scripts come only from files, per the security decision below).

## Edge cases
- Malformed frontmatter or a broken `[[link]]`; duplicate memories; an index line pointing at a missing file
- Index larger than the context budget
- Conflicting rules; a rule and a hook disagree; a hook that loops or times out; a hook that tries network or file access
- A correction that contradicts an older correction (newer wins, older kept in history)
- Unauthorised voice correction or rule attempt: from the locked phone, or the confirmation card declined → nothing stored, attempt logged in diagnostics
- Locked phone, read side: a question only memory answers gets "Unlock to continue" (E11); a before-action hook that reads memory while locked gets nothing; the phone locks mid-answer after a recall (answer stops, nothing more from memory is spoken)
- Same utterance, different output across replays of one stored test: a harness defect (frozen context inputs and pinned runtime settings should rule it out), caught by E8; a model, prompt or memory change is exactly what replay reports
- The phase 04 helper's process calling the provider: refused by the pid check (the helper has no provider verb, phase 04); the helper restarted with a new pid (the shell records the new pid at handoff and cleared the old one on binder death)
- PC push while Cortana is mid-request; push of a file with the wrong encoding
- Replay test whose target contact or app no longer exists
- Model re-downloaded or swapped (phase 08) with corrections still passing or failing visibly
- Notebook with no memories, corrections, rules or hooks yet: each list page shows its description and an empty list, with + available (approximation, H9)
- A memory name longer than one row: the label is clipped to one line at the row's right edge, since §3.3.6's rows have no second line (the full name shows on its page)
- Liveness (N-01)
