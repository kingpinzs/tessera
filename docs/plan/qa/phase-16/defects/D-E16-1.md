# D-E16-1 — a search that finds nothing says so where it cannot be seen: the line is drawn under the keyboard

(Corrected 2026-10-01 on the lead's reading of the same dump. The first version of this file said the page drew no
line at all. That was wrong: the driver's text read used a `text="…"` pattern, and uiautomator writes an attribute
whose value holds a double quote in SINGLE quotes — `text='No contacts match "Wren".'` — so the read missed it.)

- **Row / clause:** E16 — "with cross-profile contact search disabled by the profile owner …, search finds nothing
  **and says so**, and the launcher ring slice holds `[people] search "Wren": 0 (+0 enterprise)`".
- **Build:** the fix build, `app-debug.apk` md5 `3c1ad1e0e65bd919` (commit 6e524e56).
- **Found by:** `scripts/e16.sh`, run 2 on the fix build (39 passed, 3 failed, 6 recorded). Kept run:
  `qa/phase-16/E16-run2-empty-search-says-nothing-and-a-driver-dumpsys-read/` (`E16.txt`, `neg-search.xml`,
  `neg-search.png`). Two of its three failures are this row's "says so" check (the driver looked for `people_empty`);
  the third was the driver's own extra read of a legacy `dumpsys device_policy` field and is out of the driver.

## Steps
1. A managed profile (`pm create-user --profileOf 0 --managed work`, `am start-user`), TestDPC installed into it only
   and made its owner (`dpm set-profile-owner`), "Work Wren" inserted with `content insert --user <id>`.
2. People, search "Wren" → one enterprise row with the briefcase, `[people] search "Wren": 0 (+1 enterprise)` (passes).
3. TestDPC in the profile: "Managed work profile specific policies" → the switch "Disable cross-profile contacts
   search" tapped at its dump bounds.
4. The shell force-stopped and reopened (`c6`), People, the search box tapped, "Wren" typed (the keyboard is up);
   `uiautomator dump` and a screencap.

## What the device shows
```
[people] search "Wren": 0 (+0 enterprise)
PASS  with the search disabled: no row is listed                  = 0
PASS  the slice holds [people] search "Wren": 0 (+0 enterprise)   = [people] search "Wren": 0 (+0 enterprise)
```
The dump (`neg-search.xml`) DOES hold the line:
`<node … text='No contacts match "Wren".' resource-id="people_notice" … bounds="[36,1968][573,2022]">`
— in the notice band, just above the app bar's place. The keyboard that is up while a query is typed covers the
screen from about y 1423 down (the IME's visible frame), so the line at y 1968–2022 is UNDER it: the screencap
(`neg-search.png`) shows the pivot header, the search box reading "Wren", an empty black page and the keyboard.
A user who has just typed a query that matches nothing sees a blank page.

## What the spec says
E16: "search finds nothing and says so". Saying it where the keyboard hides it is not saying it.

## Diagnosis (one line)
`people/PeopleListPage.kt` sets the empty-search text as the page's notice (`notice = when { … }`), and the notice
band is laid out above the app bar at the bottom of the page — under the keyboard whenever a query is being typed;
`SearchResults` itself draws only rows.

## Note
It is every empty search, not only the work-profile one.

## Fix and the row's re-cut (the lead, 2026-10-01)
Fixed on `phase-16` (PeopleListPage.kt only; not yet in an APK): an empty search draws `No contacts match "<query>".`
with the tag `people_empty` where the first result would be, under the search box, and the notice band no longer
carries it. `e16.sh` now asserts the clause in a form that fails on this defect: `people_empty` exists, reads
`No contacts match "Wren".`, and its bottom edge is above the keyboard's top edge (the IME's visible frame from
`dumpsys window`, with the keyboard asserted up). E16 is run once on the build that carries the fix, not before.
