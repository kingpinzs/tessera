# Every component the APK exports, with its reason and the permission that guards it.
#
# Phase 03 Decisions, "Exported components allow-list": this list is written at build start from phase
# 01's components plus this phase's, and later phases ADD their own entries. E5 compares
# `adb shell dumpsys package app.tileshell` against it EXACTLY — a component that appears on the device
# and not here fails the row, and so does one here that is not on the device.
#
# The point of the row is that Cortana has exactly one way in: the text box the user can see. A
# debug intent, a broadcast or a provider verb that took a request would make every other row in this
# gate meaningless, so the surface is pinned rather than reviewed.
#
# Format: <component>\t<guard>\t<why>
# "guard: none" means the component is reachable by any app and authorises callers itself.

# ---- phase 01 ----
app.tileshell.StartActivity	guard: none (HOME intent filter)	The home screen. A launcher's HOME activity has to be exported or the platform cannot start it.
app.tileshell.weather.WeatherActivity	guard: none (LAUNCHER intent filter)	The Weather app's own launcher entry.
app.tileshell.settings.SettingsActivity	guard: none (LAUNCHER intent filter)	The Start settings launcher entry, and the settingsActivity the voice-interaction and recognition services point at.
app.tileshell.feeds.TileNotificationListener	android.permission.BIND_NOTIFICATION_LISTENER_SERVICE	The live-tile notification listener. Only the system holds the permission.
app.tileshell.tiles.api.LiveTileProvider	guard: none by design (R5 4b)	The public Live Tile API. Every call() verb authorises on the caller's Binder identity rather than on a manifest permission.
app.tileshell.tiles.api.LegacyBadgeReceiver	guard: none (legacy badge broadcasts)	Legacy badge senders resolve the shell through this entry. A sender that does not share its identity is refused by default (phase 01 adversarial review).

# ---- a library's own component, not the shell's ----

# the list because the list has to be the WHOLE exported surface to be worth anything.
androidx.profileinstaller.ProfileInstallReceiver	android.permission.DUMP	androidx.profileinstaller's baseline-profile trigger. Added by the library, guarded by DUMP.

# ---- phase 16 (task 2: the two apps' launcher entries with their intent handlers; r3 D10 / D11) ----
app.tileshell.calendar.CalendarActivity	guard: none (LAUNCHER / APP_CALENDAR; VIEW, EDIT, INSERT on events)	The Calendar app's one activity (phase 16 build task 2). An intent only chooses what is shown: VIEW a day or an event, EDIT an event (the editor only for an event in the Tessera calendar, any other opens read-only), INSERT fills the editor in and saves nothing without the user's tap, into Tessera whatever calendar_id it carried.
app.tileshell.people.PeopleActivity	guard: none (LAUNCHER / APP_CONTACTS; VIEW, EDIT, INSERT, INSERT_OR_EDIT, PICK on contacts)	The People app's one activity (phase 16 build task 2). An intent only chooses what is shown: VIEW a card, EDIT (the editor only where the write guard allows, else the card), INSERT fills the editor in and saves nothing without the user's tap, on the phone whatever account it named; PICK returns the one contact or phone URI the user tapped, with a read grant for it alone.

# ---- phase 16 (task 3: Calendar's reminder receiver; r3 D6) ----
app.tileshell.calendar.CalendarReminderReceiver	guard: none (the calendar provider's process sends EVENT_REMINDER, so any app can)	Calendar's event reminders (phase 16 build task 3). The broadcast is a poke only: nothing in the intent is read. Each poke re-reads CalendarAlerts for rows due now in state SCHEDULED or FIRED, less the alerts already notified and less a synced copy's, posts one notification per alert left and marks that row's state FIRED; it writes no other column or table.

# ---- phase 17 (task 1: the three apps' launcher entries and the three helpers other apps reach; r3 D6; Q-17-2 (b)) ----
app.tileshell.photos.PhotosActivity	guard: none (LAUNCHER / APP_GALLERY)	The Photos app's own launcher entry (phase 17 build task 1). The page extra only chooses a pivot; no data from an intent is read.
app.tileshell.photos.ViewerActivity	guard: none (VIEW on a content image); the caller check in code	The viewer other apps reach (r3 D6), in its caller's task. TRUST: ONE rule for the three helpers (media/UriAccess.kt, UriAccessRules, over the one platform port media/AndroidUriAccess.kt; trust review round 3). The intent only names the one picture, and it is read with the SHELL's identity, so who started the viewer decides (photos/ViewerRules.kt). The shell itself (the platform names the starter and it is the shell's uid) gets the picture and every action. Any other app, and an app the platform does not name, has its content URI shown only when the platform says the app that STARTED the viewer could read it: on API 35+ the platform's launch answer (getInitialCaller().checkContentUriPermission) says so; or the platform names the starter's uid and that uid owns the provider, holds a read grant for the URI, or (a forceUriPermissions provider such as MediaStore, API 35+) the provider, asked, says so. Nothing else. On API 34 an app that does not share its identity is refused. The platform's launch answer is 'denied' for a MediaStore item unless the starter holds a grant for it, so an app that only holds the media permission is shown its MediaStore item only when it shares its identity. An authority with a user id (a work-profile Open with) is handed to the platform as it is. A refused URI is never opened: the error state, `[photosapp] viewer request from <who>: refused`, `[photosapp] launch answer read: <granted|denied|threw X|not available>`, `[photosapp] refused view: no grant`. A shown picture from another app is read-only: the picture, Share, File information and a Living Image's clip; Edit, Delete and Set as are not offered. Nothing is written from an intent. Adversarial review before done.
app.tileshell.camera.CameraActivity	guard: none (LAUNCHER; STILL_IMAGE_CAMERA, VIDEO_CAMERA)	The Camera app's own launcher entry, in :camera. The mode extra and the action only choose a capture mode; captures go to DCIM/Camera through the one MediaStore write layer.
app.tileshell.camera.CaptureActivity	guard: none (IMAGE_CAPTURE, VIDEO_CAPTURE); the output guard in code	The capture answer (Q5 A, kept by Q-17-2 (b)), in :camera and its caller's task. TRUST: ONE rule for the three helpers (media/UriAccess.kt, UriAccessRules, over the one platform port media/AndroidUriAccess.kt; trust review round 3). It writes only to a content URI the four-condition output guard accepts: (a) started for a result; (b) the intent's own ClipData holds that URI with the write-grant flag; (c) not one of the shell's authorities, and no authority with @ or %; (d) BOTH (d1) the app the result goes to (getCallingPackage) may write the URI itself - it owns the provider, or holds a write grant for the URI, or (a forceUriPermissions provider such as MediaStore, API 35+) the provider, asked, says so; a permission-wide access with no grant (WRITE_CONTACTS, the system uid) is never enough, on any Android version - AND (d2) on API 35+ the platform's launch answer says the app that really STARTED the capture could write it (refused when it says no or throws), so a go-between that forwards another app's result gains nothing. Where the platform names the starter and it is not the recipient, the request is refused. On API 34 (d2) cannot be asked: (d1) alone decides, and a MediaStore row the caller owns is refused unless it holds a grant. The platform's launch answer is 'denied' for a MediaStore row unless the starter holds a grant for it, so on API 35+ too a caller's own MediaStore row is accepted only where the platform answers 'granted' for it. It refuses file URIs, an EXTRA_OUTPUT that is not a Uri and a request that cannot be read (`[camera] capture guard inputs: … callerMayWrite= recipientMayWrite= starterAtLaunch=`), and with no output returns a thumbnail (photo) or a new DCIM/Camera row with a read grant (video). A capture for a caller carries no location; a still whose location cannot be removed is not written. Adversarial review before done.
app.tileshell.video.VideoActivity	guard: none (LAUNCHER)	The Movies & TV hub's own launcher entry, in :video. The page extra only chooses a pane page.
app.tileshell.video.PlayerActivity	guard: none (VIEW on a content or http(s) video); the caller check in code	The one player (r3 D6), in :video and its caller's task. TRUST: ONE rule for the three helpers (media/UriAccess.kt, UriAccessRules, over the one platform port media/AndroidUriAccess.kt; trust review round 3). The intent only names what is played (video/PlayerRules.kt, PlayerRules.source). An http or https source plays for any caller (plain http is media: Q-D (a)); the saved media server's token rides only on the shell's own launch. A file source, a queue (EXTRA_QUEUE), a title (EXTRA_TITLE) and the .srt beside a MediaStore video are taken only when the shell itself started the player; a file path another app names is never resolved. Another app's content URI is played only when the platform says the app that STARTED the player could read it - the same READ rule as ViewerActivity's line (the launch answer on API 35+; or a named starter's own provider, read grant, or a forceUriPermissions provider's own answer); else `[video] refused source: no grant` and nothing is opened or queried; `[video] launch answer read: <granted|denied|threw X|not available>` records what the platform said. While it plays, the data source opens only http(s) addresses for a network launch, and only the launch URI itself (plus the shell's own .srt) for any other. Any other scheme is refused with its line; nothing is written.

# ---- phase 18 (task 1: the Files app's launcher entry; r3 D12) ----
app.tileshell.files.FilesActivity	guard: none (LAUNCHER / APP_FILES)	The Files app's own launcher entry (phase 18 build task 1), in the main process; ONE activity for every page. The `page` and `path` extras only choose what is shown, and a path is ignored unless it is canonical under a mounted volume (r3 D12); nothing an intent carries copies, moves, renames or deletes a file.
