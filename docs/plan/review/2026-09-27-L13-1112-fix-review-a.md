its 1.11.4 correction, activity-compose 1.13.0's `BackHandlerKt` bytecode. Read-only: no build, adb or emulator.

## Verdict: PASS

## Blocking findings

None.

## Notes

1. **The "…" menu's placement is unchanged.** ClockScaffold's Box is fixed-size (`fillMaxWidth().weight(1f)`,
   ClockTabs.kt:103). OverlayLayer measures its content with those constraints loosened, so the inner `fillMaxSize` Box
   is exactly the scaffold Box and sits at (0,0). The Column's `align(BottomStart)` resolves to the inner Box (the
   innermost BoxScope receiver). `offset(y = -height)` is unchanged. The z-order is the same as before: page, then
   scrim and menu, then the bar. All three callers go through ClockScaffold (ClockTabs.kt:163, AlarmTab.kt:263,
   TimerTab.kt:257).
2. **The cost of the always-composed Box.** Each bar gains two layout nodes, measured only when the scaffold Box
   measures. While the bar is collapsed they are never placed, and they have no pointer input and no semantics, so
   hit-testing and the dump are unaffected. Nit: putting `if (expanded)` around the inner Box instead of inside it
   would leave the layer empty (0×0) while collapsed, as the hold menus' layers are. This is not required.
3. **The bar's own height is right.** It is still the scaffold's direct child, and it takes its height from the
   `expanded` value read at composition, as before. There is a residue that existed before the fix and is outside the
   scrim's shape. For the one frame between Back and recomposition, the bar is still 68 epx tall (ClockWidgets.kt:96),
   and its buttons fill that height. A down in the 20-epx band above the collapsed bar, under Add or Select, runs that
   button. The chance is low and nothing changed here.
4. **The city search's focus and keyboard are unchanged.** CitySearch is composed and placed in the same pass as
   before, because `active()` is true whenever `nav.worldSearch` is. `LaunchedEffect { requestFocus() }` runs as it did
   before. After Back, the field stays focused but unplaced for one frame, then leaves the composition, which ends its
   input session as before. The IME still takes the first Back while it is shown. Nothing in ClockFlyout or CitySearch
   uses `Modifier.align` at its root. That matters because they are BoxScope extensions emitted into a Layout that
   ignores BoxScope parent data. It is a fragility to keep in mind, not a defect.
5. **The hold-menu BackHandlers: order.**
   - In activity-compose 1.13.0, `BackHandler` registers through `LifecycleStartEffect`, keyed on `enabled`. So each
     time a menu opens, its handler re-registers as the newest, ahead of the activity's callback from `onCreate`.
   - They are never composed together with the alarm editor's handler (AlarmTab.kt:233) or the timer name field's
     handler (TimerTab.kt:231). ClockApp composes one page at a time, and a page change disposes the tab and its
     menu state. The pager composes only the current tab plus a fresh neighbour during a drag.
   - Against ClockNav.back(), an open hold menu always closes first. That gives two edge orders, neither blocking:
     - (a) The bar sits above the page's scrim, so "…" can be opened over an open hold menu. Back then closes the
       hold menu before the bar, the reverse of the z-order. Both are visible, and every Back closes something.
     - (b) **World Clock.** Hold a city, then tap New in the bar, which is above the scrim. The search page opens over
       the menu, which is still open and now hidden. The first Back after the IME's closes the hidden menu, so nothing
       visible happens. The next Back closes the search. Before the fix, that Back closed the search. A hold on the
       search page's blank areas reaches the same state. Those areas have no pointer input: the top 8 epx, the side
       margins, and the whole "No results" page (EmptyLineR7 is plain text). Touches there fall through to the city
       list, which opens a hidden menu; this pass-through existed before the fix. The root cause is outside L13-12:
       the hold flyouts do not light-dismiss when the bar is used, and the search page is not modal. Suggested new
       ledger row: close a tab's hold menu when a bar action opens something over it, or make the search consume
       touches.
6. **The activity's dismissOverlay wrapper is correct.** `handled` is captured and `finish()` still runs only when
   `nav.back()` unwound nothing. Applying the page writes at once (editor to Tabs, and so on) only schedules
   recomposition earlier, since no layout phase reads `page`. The callback runs from a key event or from the drawn
   Back's click, never from inside composition or `applyChanges`, so `sendApplyNotifications` is safe there.
   ClockNav's KDoc ("Back unwinds the innermost mode first…") does not mention that hold menus now sit ahead of it.
   That is a doc nit only.
7. **Nothing else in the Clock has the shape.** The shape is a full-screen scrim that eats a touch meant for a visible
   page after a plain-write Back.
   - ClockFlyout's other users, the three alarm-editor flyouts, are already in L13-9's OverlayLayer.
   - The timer editor has no overlay. Its name field's handler is a plain write, but there is no scrim.
   - The expanded timer and the expanded stopwatch are pages. The stale frame hits the old page's own visible
     controls, which is the ordinary one-frame page change and not a hidden scrim.
   - The stopwatch tab has no overlay and no hold.
   - The compare strip is a 54-epx strip with no scrim. In the stale frame a down there can land on ‹ or › instead of
     the bar under it. The chance is low, and this is the same class as note 3.
   - SoundsScreen and MusicPickerScreen have no overlays.
8. **Outside my lens, for B: the L13-11 (b) before-run count is contaminated.** The driver's cleanup for a `menu`
   outcome is one Back (l13_11_row.sh:80). On a7c9d715 that Back closes the Clock, which is L13-12's bug. The next
   trial then starts outside the Clock and scores `other`. In `L13_11-before-a7c9d715/b/trials.txt`, all 12 `other`
   outcomes directly follow a `menu` outcome. In the 18 clean trials, 5 holds were lost (`tabs`). So the row still
   fails before the fix and the rule holds, but the ledger's "search 13/30" overstates it. The honest figure is 13 of
   18 clean trials passed, 5 lost. Bar case (a) is clean: its cleanup Back from the editor lands on the tabs, so
   its 19/30 stands. Both before-run headers print `apk built 05e543d7… / apk match NO`, naming the tree rather than
   the installed build.
9. **Scope.** L13-12's fix adds a Back write path to three menus. Putting them in OverlayLayer is what keeps that
   path from creating a new instance of L13-11's shape, so it is in scope. The tap-offs and the verbs stay plain
   writes, consistent with L13-3's precedent (plan amendment 2, note 5).
