## 1. Contradictions with FINAL docs, standing rulings and the Android limits

**1. BLOCKING — R10-Q3 rests on a misreading of the measured and built hold.** `docs/plan/PLAN.md:214-221` says
"R6 §1.1.1: a hold enters edit mode on release" and that the threshold and the drag "stay as measured; only a hold released
without a drag now opens the burst". R6 §1.1.1 (`docs/plan/r6-measurements.md:80`) measures 783 ms from touch-down to the
FIRST CHANGED FRAME — the edit-mode entry starts with the finger still down, and phase-02's Decisions line
(`docs/plan/phase-02-edit-mode-folders.md:28`) and E7 (`:67`) measure the 417 / 550 ms entry from that point. The code does
exactly that: `app/src/main/kotlin/app/tileshell/start/EditGestures.kt:78-85` calls `edit.enter()` at the 783-ms timeout and
only then waits to see whether the finger moves ("lifting it leaves the tile held with its two discs"). So under R10-Q3 the
state between 783 ms and the release is undefined. Either (a) edit mode enters at 783 ms as measured, in which case the
release opens a burst ON TOP of edit mode and the "Edit" satellite enters a mode that is already on — and W10M's measured
hold-to-edit no longer exists on its own, since every release now adds a burst; or (b) the entry is deferred until the finger
moves, which gives up R6 §1.1.8 / §1.1.9 (entry begins at 783 ms, not at first movement), starts R6 §1.3.1's "dragged tile
follows the finger while the others keep the edit-mode scale" and the entry contraction in the same frame, and moves E7's
measurement origin. The ruling cannot be split into a phase until one is chosen. Two options plus an escape, for Jeremy:
A. the launcher convention the ruling itself cites (Pixel / One UI): at 783 ms edit mode enters as measured AND the burst fans
out from the held tile; a drag dismisses the burst and moves the tile; a release leaves the burst up until a tap elsewhere or
Back; "Edit" is dropped because edit mode is already on, which frees the fourth slot for a shortcut — every R6 number keeps
its meaning. B. as ruled: nothing visible at 783 ms (R6's "no feedback" extended past the threshold), release → burst, first
movement → entry and drag in one gesture — then phase-02 Decisions :28, E1 :61, E7 :67 and H1 :73 are re-specified with the
entry measured from first movement, and R6 §1.1.1's measured entry point is knowingly given up. Either way, note that "Edit
enters edit mode on that tile" describes what a hold already does.

## 2. Feasibility on unrooted Android 16 / One UI 8 the plan glosses over

**18. BLOCKING (for the overlay half of R10-Q1) — cross-window blur on the S25U is not proven, and cannot be seen on the
AVD.** `WindowManager.isCrossWindowBlurEnabled()` is API 31+, requires `ro.surface_flinger.supports_background_blur=1`,
and is off under Battery saver and the "Disable window blurs" developer toggle. Galaxy devices have been reported to return
false because One UI blurs through its own private path — reported, not verified for One UI 8. The AOSP AVD does not set the
property, so the action center / volume panel acrylic (phase 04) is untestable on the emulator whatever the phone says. What
settles it, one adb session, added to R4's phone list (`phase-04:110-119`): `adb shell getprop
ro.surface_flinger.supports_background_blur`; `adb shell dumpsys SurfaceFlinger | grep -i blur`; a probe overlay window with
`FLAG_BLUR_BEHIND` + `setBlurBehindRadius` that logs `isCrossWindowBlurEnabled()` and `addCrossWindowBlurEnabledListener`,
with a screencap; the same with Battery saver on. If false, the overlay surfaces get finding 5's fallback form and only
the in-app surfaces (app list, menus, pod bay) are acrylic.

**19. SHOULD-FIX — the in-app acrylic engine needs one permanent form (RV2 / Rule 16) chosen before the split.** Compose
`Modifier.blur` is API 31+ RenderEffect on the element's OWN content (R10 item 3 is right, `r10-secondary-spec-review.md:50`).
A blurred backdrop in-app is one of: (a) a pre-blurred copy of the shell's own Start background — static and cheap, and the
right answer for the app-list backdrop, because what is behind the app list IS the shell's wallpaper; (b) per-frame capture
of live content under a menu (`rememberGraphicsLayer` + RenderEffect) — a full-resolution layer per frame at 1440x3120, so
a phone P-row on frame time (`dumpsys gfxinfo`) and, over flipping live tiles, the same never-idle screen RV13 already had to
work around; (c) a library (haze) — a new dependency needing an R2-style licence check. Name which surfaces use (a) and
which (b). No code in the tree does any of this yet (no RenderEffect / blur / cross-window call under `app/src/main/kotlin`).

**20. SHOULD-FIX — App Shortcuts are feasible with four unstated conditions.** `LauncherApps.getShortcuts` needs
`hasShortcutHostPermission()` — true for the HOME role holder (QA and phone), but false during the wizard before HOME is
granted and whenever the user switches home back: it throws SecurityException, so the burst must degrade to "Edit" alone
rather than crash. Private-space shortcuts are visible only while that profile is unlocked (`AppCatalog.kt:144` already
tracks profiles). Icons from `getShortcutIconDrawable` are app-drawn colour icons with no monochrome layer, so satellites are
not white-on-accent unless drawn by phase 01's glyph rule (H38: monochrome layer where provided, else full colour — extend
it to shortcuts). Launch is `startShortcut(pkg, id, sourceBounds, options, user)` per user handle, and
`LauncherApps.Callback.onShortcutsChanged` should refresh an open burst (the one callback lives in `AppCatalog.kt:54`).
A11 holds — nothing here touches the network.

**21. SHOULD-FIX — satellite geometry and motion are unspecified beyond two numbers.** `PLAN.md:183-189` gives
boundsInRoot and dampingRatio 0.65 and nothing else: satellite size (a small tile? a 31-epx disc like the edit discs?),
distance from the tile, the four angles, labels (a shortcut with no label is unreadable — W10M tiles carry labels),
stiffness (a spring has no duration; RV11's pass rule needs a settle envelope computed from the spring parameters), stagger,
and dismissal (tap elsewhere, Back, Home, scroll, screen off). Off-screen cases: a tile at a screen edge, a wide tile at the
right edge in 2-column mode, a bottom-row tile (satellites land on the nav bar or on the other row tiles), and the promoted
tile above the row (`INDEX.md:66`: lifted out of the grid — "Edit" on it selects a tile that is about to jump back to its
grid cell). Build note: boundsInRoot is wrong if the satellites are drawn in a Popup / Dialog (a different window root); they
must live in the Start composition root, and the phase-02 gate's lesson applies — a sibling layer over the grid swallowed taps
(`phase-02:122-124`). All of this is P4 design and needs an H-row: `PLAN.md:186-187` says no row "can be closed against
footage", which is not the same as no row (Hard Rule 15; P4 at `PLAN.md:84-87`).

**22. NOTE — most tiles will have no shortcuts.** F-Droid-style apps rarely declare any; Samsung's do. The shell's own
in-APK apps (Music, Weather, Tess, Start settings, and every inbox app to come) can declare static shortcuts in their own
manifest (`android.app.shortcuts` meta-data). Decide now whether they do, because "Edit alone" on every shell tile makes the
burst feel empty on exactly the tiles the shell controls.

**23. SHOULD-FIX — the wizard's contract with the checklist.** It must reuse the checklist rows
(`app/src/main/kotlin/app/tileshell/onboarding/Checklist.kt:73-105` is already a list of rows, each with a grant action), grow
by ADD as each phase adds rows (phase 03's assistant / microphone / contacts / …, phase 04's accessibility / overlay /
Wireless-debugging pairing), and must not re-run on an update install over an existing layout — use the LayoutStore
version-marker precedent, not a fresh-install heuristic. State what it shows when rows are already green (the drivers grant
roles by adb before first launch). It has no fidelity source: W10M's OOBE was not measured by R3 / R6 / R7, so it is P4 design
with an H-row; and "picks the accent" (`r10-secondary-spec-review.md:63`) must write the same X26 setting as Settings > Start
+ theme, not a second one.

**24. SHOULD-FIX — the wizard sits in front of every existing driver.** Phase 01–03 rows start from a wiped state
(`INDEX.md:40`, RV12) and provision.sh sets the preferred home by adb; a first-run wizard is the first thing every driver's
Start now meets. Phase 03 forbids test-only injection paths for requests (`phase-03:37`); the same spirit rules out an
adb-settable "wizard done" bypass. The honest route is a real, user-visible Skip on optional pages (W10M's OOBE had one),
driven once by the harness, plus a wizard E-row that drives every page. Decide before the split, or the phase 01–03 evidence
cannot be re-run on a wiped state.

**25. SHOULD-FIX — pod-bay swipe vs gesture navigation.** If the pane opens on an edge swipe from the left, the system Back
gesture takes it — the shell hides the bars but the edge gesture still fires (phase-01 E19 `:204` shows the edge swipe
revealing transient bars), and `systemGestureExclusionRects` is capped at 200 dp per edge. A pager pan (any x on Start) has no
conflict. Rule: pan, not edge swipe. Emulator-testable in both modes (`settings put secure navigation_mode 2 / 0`, as
phase-04 P5 already does); One UI's own gesture handling is a phone row.

**26. NOTE — feasibility by inbox app** (each new permission is a checklist row):
- Camera: Camera2 or CameraX (a Google Jetpack library — P5 wants the stated reason; raw Camera2 needs none). Widely

- Alarms & Clock: `setAlarmClock` (Doze-exempt; shows as the next alarm on Samsung's lock screen); ringing over the keyguard

- Calendar / People: provider access already held (`AndroidManifest.xml:30,41,43`); People needs WRITE_CONTACTS to edit; no

- Photos: READ_MEDIA_IMAGES held; edits need `MediaStore.createWriteRequest` (a system dialog per batch) unless Files'

- Voice Recorder: RECORD_AUDIO held; write with IS_RECORDING (finding 14).
- Video player: reuse phase 10's Media3 engine (RV2); DRM out.
- Calculator: nothing.

## 4. Split proposal

**31. NOTE — phases, order, and which shipped phases each touches.**
- **11 Tile quick actions.** Touches 02 (EditGestures, Decisions :28, E1, E7, H1) and 01 (dock tiles, promoted tile).
  First: smallest, it changes shipped gesture code that phase 02's deferred re-runs will re-verify, and its fixture is
  cheap — add a `shortcuts.xml` to phase 02's own client-library test APK (`phase-02:65`) instead of depending on which
  AOSP apps declare shortcuts. Cannot start until finding 1 is ruled.
- **12 First-run setup wizard.** Touches 01 (checklist, HOME flow, every driver's provisioning) and 03 (its rows). Second:
  every later phase adds rows to it and every driver on a wiped state meets it, so build it before more rows exist and
  before the harness has to change twice.
- **13 Fluent materials.** One permanent acrylic engine (in-app blurred backdrop + tint + noise, plus the cross-window path
  for overlay windows) applied to the app-list backdrop and the surfaces finding 3's table names; touches 01 (app list), 02
  (H21 menu), 03 (pane / menu if listed), 10 (hold menus). Before 04, because Rule 16 says 04 builds the action center in
  its final form, so the engine must exist when 04 starts. Its cross-window half is proven only by finding 18's probe, so
  the overlay acceptance is a phone row and the emulator rows are the in-app surfaces.
- **14 Pod bay.** Pane + pods (reusing the Calendar / Weather / Music feeds and the reminder store) + Tess's command (ADD to
  the matcher, the action layer and the locked gate); touches 01 (pivot, Back on Start), 03 (matcher, action layer, exported
  allow-list), 07 (name only). After 12 / 13 so the pane is acrylic from day one and the wizard already exists. **14b
  Android widgets**, only if finding 7 rules them in — a seam-heavy part (picker, bind consent, configure, host lifecycle)
  with nothing in common with the pods.
- **15–24 Inbox apps**, one phase each, each gated by its own measurement task (finding 10), in this order: Calculator
  (no permissions; proves the second-in-APK-app template after Music); Alarms & Clock (unifies exact alarms with 03's
  reminders and gives Tess's alarm / timer commands a home); Calendar, People, Photos (slot exists, provider access held,
  feed exists); Voice Recorder (re-asks Q6); Video player (Media3 from 10); Camera (largest platform risk, own process,
  phone-heavy QA); Files (All-files-access row; also unblocks Photos' edits); Settings front LAST — it aggregates every
