## Blocking

**B1. L13-3: the evidence does not support "fixed", and the gate passed the unfixed build.**
- **The gate passed the old build.** `L13_3-before-ee4bf960-emu5558/L13_3.txt` (17:01) scores 10/0 on the old build. That build is installed md5 33e487ea, which the 5554 before-run header matches to ee4bf960. So the row can fail, but it does not reliably fail before the fix.
- **The 70-trial half never discriminated** (`l13_3_row.sh:17-26`).
  - 0 of 280 trials were lost across all four runs, old and new builds alike.
  - Host timing was the same in every `g0/summary.txt`: back->B0 median 4 ms, K0->K1 12-13 ms.
  - The fix plan's "fails before (the investigation lost 5 of 70)" did not reproduce in this era. The 140 after-trials add no evidence.
- **Only the host loop discriminated, and only on 5554** (`l13_3_row.sh:27-33`).
  - Before: 2 of 3 loops lost holds (12:29).
  - After: 0 of 8 loops lost holds (3 in the row at 16:42, plus 5 ad hoc at 17:14).
  - Like for like, Fisher's exact test (one-sided) gives p = 0.055.
  - Pooling the old build across every session gives p = 0.031: 8 of 24 loops lost holds (the investigation's table plus both row runs), against 0 of 11 after (8 on 5554, 3 on 5558).
  - The 5554 pair is four hours apart, and host load is not logged: the row does not write sweep's loadavg line.
  - The 5558 pair shows that conditions exist in which the old build passes.
- **No after-run shows the race window was exercised.**
  - The product ring has no Back or down timestamps, so a pass cannot be told apart from "no down fell in the window".
  - The diagnostic builds did measure the window on 5554 at about 16:27. A down was handled between `back closes band` and `band left composition` in 4 of 8 host loops (`L13-3-diag-on-fix-e4dedc5e/hostloop-1..3`, `L13-3-diag2-row-events-5d1a37d5/hostloop-3`).
  - If that rate held from 16:42 to 17:16, a broken fix would pass 8 of 8 loops with p ≈ 0.004. That is suggestive, but it assumes the rate held, and the 5558 run is a counterexample.
- **Failure scenario:**
  - The dismissOverlay/OverlayLayer path leaves some window open, for example a touch dequeued before the Back's apply.
  - Holds are then still lost at the old rate of about 1 loop in 3.
  - The after sessions passed only because no down landed in that window, which is exactly what happened to the old build on 5558.
- **To close it, either:**
  - (a) Apply only diag.patch's `[l13]` timing lines (back closes band, band left composition, row down, scrim down) to 9a801834. Run at least 10 host loops on 5554. Show at least 3 downs handled after the Back but before `band left composition`, each reaching the row, with 0 scrim downs and 0 lost bands. Or:
  - (b) Run an interleaved same-session A/B on 5554: alternate ee4bf960 and the fix build, at least 15 loops each, with loadavg logged per loop. The old build must lose holds in that session and the fix must lose 0 of 15. At the pooled rate, (2/3)^15 ≈ 0.002.
- Until then, the ledger should say "fix in, device evidence suggestive", not "fixed".

**B2. L13-4: the fix changes how Back queues, and the row cannot see it. Device output on d6a364c8 shows the regression.**
- **The code** (9a801834 `StartActivity.kt`):
  - `backEvents` has `extraBufferCapacity = 1` (:89), and the pivot now runs in `launch {}` (:169-177).
  - Before the fix, a second Back during the pivot waited in that buffer until the pivot finished. It then ran as `backOnStart()`, which returns to the last app (X12).
  - Now the collector returns at once. The second Back still sees `currentPage == 1`, starts a new pivot and cancels the first, so Back on Start never runs.
- **The new diagnostics line is not evidence of a touch.** The catch (:173, and Home's at :154) labels *every* CancellationException "pivot interrupted by a touch": a preempting pivot, or the activity being destroyed.
- **Device evidence:** `L13_4-twice-red-d6a364c8/L13_4.txt` (17:20, installed 46b644dc, match yes). `input keyevent 4 4` from the app list gave:
  - FAIL "the second Back ran as Back on Start": there is no `[back]` line.
  - FAIL "no pivot was cut short": the slice has `[start] back: pivot interrupted by a touch`, and no touch was sent.
- **The committed row cannot fail on this change.** Row blob 2309ace3, behind `L13_4-fix2-d6a364c8`'s 19/0, only tests Back, Home and the drawn Back after a touch. Its 19/0 supports "Back and Home survive a touch". It does not support the commit's "Back and the Windows key keep working".
- **Failure scenario:** a person presses Back twice quickly from the app list to return to the last app. The second press is swallowed, or, later in the pivot, runs mid-slide (not measured).
- **What is left to do:**
  - The working tree already has a StartActivity change and a `twice()` step. `twice()` has failed on d6a364c8 (done).
  - It must pass on the new build, and it must pass on ee4bf960, to show the step does not fail for its own reasons (not yet shown).
  - Then re-run every row (L13-2/3/4/5 and unit) on the new build, into new directories. ModalOverlay.kt and MusicCollectionPage.kt changed too: the grid's cell-tap dismissal no longer goes through `dismissOverlay`.

## Non-blocking notes

**N1. The jump grids are not covered.**
- 9a801834 also moved the app-list jump grid and Music's jump grid into OverlayLayer.
- No device row tests a touch right after Back closes either grid. The L13-2 row only shows they stay modal while open.

**N2. At 9a801834, L13-3's rule masks L13-5's.**
- In the row's scenario (Back while holding Pin to Start), the item gets both `lifted=false` and `open=false`.
- So the device row still passes if either wiring in `overlayItem` is broken (`!change.isConsumed` or `active()`). The unit tests cover only the pure `OverlayItemPress.lift`.
- To isolate L13-5's rule, test a removal without a dismissal: an overlay that leaves composition while `active()` is still true.
- There is also no device evidence for "a real lift after the dismissal and before the removal runs nothing".

**N3. L13-5's before-run used a different driver.**
- The before-run used blob 600b9e93. It was not kept (untracked at the time).
- The after-runs use d255c67c (edited at 16:07), which adds a baseline restore before step (2).
- Step (1)'s assertion names match in both. The before-run's `held-slice.txt` holds the pin line, so step (1) would fail on it.
- But the committed driver has never run on a pre-fix build. Re-run it on ee4bf960 to meet the rule literally.
- Step (1) has no positive marker that the press reached Pin in the after-run: its slice is `tile_anim` lines only. It relies on step (2)'s separately computed control.

**N4. The L13-4 driver drops its own evidence.**
- `l13_4_row.sh:29` force-stops between cases without calling `ring_save` first, against lib.sh's own rule. Only the last case's ring survives.
- So for back-press and home-press on the after-build, the only kept sign that the pivot was interrupted is the RECORD "applist" after the first key.
- `page()` (:17-24) reads any dump that is not the app list, including "(dump failed)", as "start". That is fail-open, though no kept dump actually falsely passed.

**N5. Build and device provenance.**
- Headers stamp only the row wrapper and lib.sh. They do not stamp `l13_3_race.sh`, which holds the trial verdict and the host loop, or `p13.sh`. Their edit times (12:23) predate every run, so it is fine this time.

- d6a364c8 was built from an uncommitted tree: its first run was at 16:42, and 9a801834 was committed at 17:01. No tree hash ties the build to the commit.

- The 5558 before-run header reads "apk built d6a364c8 … match NO". The build under test there is only the installed md5 33e487ea.

**N6. The fixed row directory can mix runs.**
- `row_begin` (lib.sh:60-84) writes to a fixed `$QA/$ROW`: it truncates the log but appends to `ring-*.txt`.
- The host loop writes `summary.txt` only at its end (`l13_3_race.sh:159`).
- So a reused directory mixes runs, or lets a crashed loop read a stale PASS summary.
- Every run was renamed this time, but `L13_4/` was reused twice within five minutes while I reviewed.
- Suggestion: make `ROW_DIR` default to `<row>-<apk>-<time>`.

- Its `summary.txt` gives "build installed" as a pm path, not a hash. `setup.txt` does carry 46b644dc.
