## Per fix

- **L13-3 (`ModalOverlay.kt:39-61`, `AppListPage.kt:240-241, 331-362`, `MusicCollectionPage.kt:469-476`).** Correct.
  `dismissOverlay` applies the write, so the layout observer runs synchronously and `OverlayLayer` is queued for
  relayout inside the Back callback. The next touch's `handleMotionEvent` then lays out first and leaves the overlay
  unplaced, and `hitTestChild` never visits it. The down's path therefore holds no overlay node, and the removal a frame
  later cancels only the overlay's own path. Checked:
  - Opening: placement reads `active()` and places the content whenever it is true; the content arrives by the usual
    recomposition.
  - Modality while open (L13-2): unchanged; the overlay is placed and topmost.
  - Constraints and size: the same as the Box children they replace.
  - The lambdas are memoised under strong skipping (Kotlin 2.4.20, no compiler flags), so the static local and the
    measure policy do not churn.
- **L13-4 (`StartActivity.kt:137-180`).** Correct. The `launch` inside `collect` binds to the `LaunchedEffect` scope.
  A `MutationInterruptedException` is a `CancellationException`, so it cancels the child only; the collectors live on.
  The rethrow keeps the child cancelled.
- **L13-5 (`ModalOverlay.kt:121-131, 159-163`).** Correct. Every overlay item is a descendant of its `modalOverlay` root
  in the hit path (band `AppListMenu.kt:122-178`, grids `AppListPage.kt:616-659`, `MusicCollectionPage.kt:779-826`).
  The root consumes only in Main, after its items. The one Initial-pass handler above an item (`revealLights`) observes
  and does not consume. So a real lift reaches the item unconsumed, and the synthetic one does not.
- **Leftovers of b2d44b7d.** `releaseInputWhenDismissed`, the two early returns and `modalOverlay`'s `active` read are
  gone. The imports are clean. `LocalOverlayActive` remains, now only for the `open` guard (note 1).
- **Music's grid Back handler (`MusicCollectionPage.kt:778`).** It is still composed inside the grid, so it registers
  last and wins, as before. For the one frame between dismissal and removal it still takes a second Back. That was also
  true before the fix.
- **`sendApplyNotifications` from a Back callback.** Safe:
  - activity-compose 1.13.0's `ComposeBackHandler.onBackCompleted` invokes the lambda directly, on the main thread,
    outside composition and outside any snapshot;
  - the Recomposer's apply observer only records the change and resumes through the dispatcher;
  - layout invalidation only schedules work.

## Non-blocking notes

1. **The `open` guard's stated reason is wrong: an unplaced item gets no events at all.**
   - Bytecode: `Node.dispatchMainEventPass` @36-71 and `Node.dispatchFinalEventPass` @33-67 return `false` when
     `modifierNode.coordinator.layoutNode.isPlaced` is false. That covers Initial, the children and Main.
   - So after a `dismissOverlay`, the held finger's next event (its up included) lays the overlay out first. That event
     never reaches the item or the scrim.
   - Three texts claim otherwise ("a real lift in that frame reaches the item"):
     - the amendment's "Items" bullet;
     - `ModalOverlayTest.kt:101-102`;
     - the `lift` KDoc and the comment at `ModalOverlay.kt:122-125, 154-158`.
   - Where `open` actually matters: a dismissal that was written but not yet laid out. That happens only on paths that
     do not use `dismissOverlay`: ON_STOP, `LaunchedEffect(visible)`, the app list's tap-off and picks.
   - The guard is harmless, but the text should say what it covers.
   - Mutation: `aLiftAfterTheOverlayWasDismissedRunsNothing` pins the rule. Nothing pins the wiring: if `OverlayLayer`
     stopped providing `LocalOverlayActive` (default `{ true }`), no unit test or row would fail.
2. **L13-5's row on d6a364c8 no longer tells the `lifted` rule apart.**
   - After a Back, the held item is first unplaced (no events), then cancelled with `open = false`. The row passes with
     or without `lifted`.
   - The run that does isolate the rule is `qa/phase-13/L13_5-fix1-598ca8c2/` (b2d44b7d, before `OverlayLayer`). The
     ledger should cite that run as L13-5's proof.
   - Where `lifted` is still the only guard: a removal while the overlay is still open, e.g. the whole page leaving
     composition.
3. **L13-4 changes when Back and Home events are processed, and the plan does not say so.**
   - Before: the collector was suspended during the pivot, and `extraBufferCapacity = 1` queued the second Back. It
     always ran after the pivot settled (`backOnStart()`, the X12 back-history launch).
   - Now a second Back runs at once:
     - in roughly the first half of the pivot, `currentPage == 1`, so it restarts the pivot and the history launch is
       lost;
     - in the second half, `backOnStart()` starts Start's exit animation while the pager is still settling.
   - The investigation's other option keeps the old ordering: catch the animation's interruption inside the collect and
     rethrow only when the effect itself is cancelled.
   - The outcome for an ordinary double Back is the same most of the time. Record it in the ledger or keep the ordering.
4. **The L13-4 diagnostics can blame a touch that did not happen (`StartActivity.kt:153-154, 172-173`).** The same
   `catch` fires when a later Back or Home interrupts the pivot (MutatorMutex, same priority), and when the effect is
   cancelled on teardown. Each logs "pivot interrupted by a touch". That could mislead a future investigation that reads
   the `[start]` lines.
5. **`dismissOverlay` is used unevenly.**
   - Music's grid routes its tap-off, semantics click and Back through it (`MusicCollectionPage.kt:471`).
   - The app list's band tap-off (`AppListPage.kt:337`), its grid tap-off (`:360`) and all picks do not.
   - The practical gap is nil: one finger cannot put a down in the queue before the posted apply runs.
   - One side effect: Music's `onDismiss` also runs from the scrim's synthetic tap-off when the grid is removed under a
     still finger. `sendApplyNotifications()` then runs inside `Recomposer.applyChanges`, during the node detach. The
     write is a no-op there and Compose tolerates it, but no one designed or tested that path.
6. **The same shape remains in Music's hold menu (outside the ledger's scope).**
   - Music's Back writes `menu = null` (`MusicCollectionPage.kt:177-184`).
   - The `MusicMenu` band, with its full-screen scrim (`MusicPlaylistUi.kt:60-74`), is a later sibling in the overlay
     box (`MusicCollectionPage.kt:327-338`) and is not in an `OverlayLayer`.
   - A hold on a track within a frame of that Back is lost exactly as L13-3 describes. The same goes for the naming box
     and the now-playing `•••` menu.
   - The investigation's list left it out, so the fix rightly did not touch it. It deserves its own ledger line.
7. **The ledger has not caught up.** `INDEX.md` has not changed since 216e67e4. L13-3 still reads "cause found", L13-4
   and L13-5 "open", and there is no Change Log entry for b2d44b7d or 9a801834. The plan says both will record the
   fixes.
