## The producer (checked, holds)

1. **The bar callback sees every open.** Only the "…" button's `onExpand(!expanded)` passes `true`. Save, Delete, the
   scrim and the menu items pass `false`; ClockNav only ever writes `false`. The end happens in the same write as the
   open, with no frame lag (an L13-13-style LaunchedEffect would leave one frame with both). `if (it)` leaves closes alone.
2. **The same rule as L13-13, L13-17 and L13-19:** opening the menu collapses the transient layers under it. The
   alternative, disabling the editor's BackHandler while `barExpanded`, would fix the Back order but leave a focused field
   with a live input session under the scrim, which a floating or hardware keyboard would still type into.
3. **Scope.** The row's first half is left alone: the edit mode outliving the keyboard (Back hides the IME, a second Back
   ends the edit). That is pre-existing design, not this defect. The fix covers the menu with or without the keyboard.

## Keyboard, name, focus (checked, holds)

4. **Keyboard up + "…" is unreachable with a docked IME.** The emulator's IME window [0,1422][1080,2205] covers
   `clock_more` [936,2052][1080,2196] (the a-2 / a-3 dumps and `.windows`). The window is neither resized nor panned:
   `setDecorFitsSystemWindows(false)`, no imePadding, and the field's bounds are the same with and without the keyboard.
   It is reachable with a floating or split IME, or with a hardware keyboard.
5. **In that case it is the Done path.** A custom `onDone` suppresses the default action, so Done only sets
   `editingName = false`, and both paths remove the focused field. By bytecode, the String BasicTextField is the legacy
   CoreTextField. Its LaunchedEffect `finally` runs `endInputSession`, then `TextFieldDelegate.onBlur` (the value with
   `composition = null`, then `session.dispose`). The adapter's `stopInput` cancels the method session.
   AndroidPlatformTextInputSession's cancellation handler then calls `TextInputService.stopInput`, and from there
   `PlatformTextInputService.stopInput`, TextInputServiceAndroid's StopInput, `setKeyboardVisibleImmediately(false)` and
   `hideSoftInput`. Nothing else starts input in that frame, so the StopInput is not coalesced away and the keyboard
   is not left up.
6. **The name is not lost.** Every edit is already in the draft: the String BasicTextField passes the whole text to
   `onValueChange`, the composing region included. `onBlur` only clears the composition; the string is unchanged, so
   there is no extra callback. An unconverted composition (kana, say) is committed raw, the same as on Done.
7. **Focus.** Detaching the focused node clears focus to the root, as Done does. Tapping the name again composes the
   field again, and its `LaunchedEffect` requests focus.

## Back order (checked, holds)

8. **Every state:**
   - Keyboard up: the IME takes Back. Unchanged.
   - Edit with no keyboard, or a flyout (alarm): the editor's handler. Unchanged.
   - Menu up: the open cleared the flyout and the edit, and the scrim covers the rows, so the editor's handler is
     disabled. Back reaches `nav.back()`, which closes the menu and leaves the editor (a-5 / b-5). The next Back goes
     to Tabs. Unchanged.
   - Menu with the keyboard up: no longer reachable (items 4 and 5).
9. **The menu state no longer depends on handler ranking.** Only the activity's callback is enabled there, so how
   activity-compose 1.13.0 ranks BackHandler (through NavigationEventDispatcher, re-added on start) cannot matter.
10. **A Back in the same frame as the "…" tap** meets the handler still enabled, which re-writes `editingName = false`.
    It is swallowed harmlessly, as in L13-19.

## The same shape elsewhere in the Clock (none found)

11. **All five BackHandlers in clock/ are covered.** Three are the tab hold menus, which L13-13 closes on
    `barExpanded`. The other two are the editors, where both layers now end on the open. Select, the city search and

## Notes (none blocking)

1. **Edge-triggered, not an invariant.** A second finger can still reach menu + edit:
   - A finger held on the name row while "…" is tapped, lifted after the scrim is up. Its up follows its original hit
     path, so `editingName` becomes true and the field and keyboard come up under the menu.
   - Or a new finger-down on the row within the frame after the "…" up.
   The old Back order then returns. This is L13-19 note 2's edge, and contrived. Gating the handler with
   `&& !nav.barExpanded`, or the row tap with `!nav.barExpanded`, would make it structural. Optional.
2. **The city search under the menu (pre-existing, not this shape).** Its field keeps focus and input under the
   scrim, so a floating or hardware keyboard edits the query under the menu. Its Back order is right: IME, menu, search.
3. **Coverage gaps:**
   - The keyboard-up "…" path rests on code and bytecode. No row proves that Done hides the keyboard either, though
     it is the same path.
   - No case re-enters edit mode after the menu (focus and keyboard back).
   - No case picks About or Notification settings from the menu with an edit open.
   - No case has an uncommitted composition (`input text` commits).
