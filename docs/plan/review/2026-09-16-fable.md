# Pre-split review — Reviewer 1 (Fable), 2026-09-16

Lens: design, correctness, Android/Samsung feasibility. Inputs: PLAN.md, w10m-reference.md (R1), r2-reuse-check.md (R2). Web checks are cited by URL; anything not cited is my own Android knowledge and is marked "(unverified; QA on phone)".

Severity: BLOCKING = settle before the split · MAJOR = changes one phase's goal/QA and must be named in the split · MINOR = record it, decide in the phase interview.

Counts: BLOCKING 8 · MAJOR 12 · MINOR 9.

## BLOCKING

### B1. Scaling, display-resolution setting and column default are unruled; R1's arithmetic assumes a setting the phone does not ship in
- Claim: phase 1's design tokens cannot be written. R1 leaves the epx→dp choice open, PLAN.md never picks, and both assume a 1440-px-wide framebuffer.
- Evidence: PLAN.md:30 "6.9\" 1440x3120"; PLAN.md:31 "The emulator AVD should match its resolution and density" (density never stated); R1:355 "Pick one and state it in the design tokens"; R1:353 "Option A … 1 epx = 4 px"; R1:356 "at ≥3.5 px/epx that is the only plateau that will not upscale". Verified: the S25 Ultra ships at FHD+ 2340x1080 and QHD+ is an opt-in setting (https://www.sammobile.com/news/samsung-galaxy-s25-plus-ultra-settings-to-change/ ; https://www.howtogeek.com/tweak-these-settings-to-get-the-best-out-of-your-galaxy-s25s-display/). Reported density is 450 dpi at FHD+ and 560 dpi at QHD+ (https://xdaforums.com/t/understanding-dpi-values-s25-ultra.4723164/). [derived] dp canvas: 1080/2.8125 = 384 dp wide at FHD+, 1440/3.5 = 411 dp at QHD+ — the epx→dp factor differs per setting, and "1 epx = 4 px" becomes 3 px at the factory setting. Samsung's "Screen zoom" slider changes density again.
- Decision (one question, three parts): Which display setting is the project's fixed QA precondition — FHD+ (factory) or QHD+, at default Screen zoom; Option A (360-epx canvas, ~13% larger than a Lumia 950) or Option B (950 physical size, more rows); and is the S25U default 2 medium columns or 3 ("show more tiles" default)?

### B2. Phase 1 "animated live tiles" has no real data to animate until phase 3 — mock (Rule 4) or no-op
- Claim: on W10M a tile with no notification does not animate; phase 1 has no notification feed, so its "animated live tiles" can only be driven by fake content, or cannot be QA'd.
- Evidence: PLAN.md:79 "1. Start screen: animated live tiles, press tilt, …"; PLAN.md:83 "3. Live tiles (notification-driven, Photos, Calendar, Music, Weather)"; R1:93 "without the queue they flip once and stop". Rule 4 forbids mocks; Rule 16 forbids a placeholder engine replaced later.
- Decision: Re-cut so the tile-animation engine lands with its first real feed — which feed is first: Weather (A11 makes it the only internet feature, needs no special permission, so it can be phase 1's real feed) or Calendar/Photos (permissions only)? Or does phase 1 ship static tiles and the engine moves wholly into phase 3?

### B3. Settings placement blocks phase 1 QA
- Claim: phase 1 lists accent color, and the feature list puts background image and "show more tiles" on Start; QA under Rule 4 needs a real UI to change them, and Rule 16 forbids a throwaway settings screen. "Settings screens" cannot be one late phase.
- Evidence: PLAN.md:89 "(Settings screens: placement to decide at the split)"; PLAN.md:79 "accent color"; PLAN.md:50-51 "'show more tiles' column option, full-screen background image"; R1:70-72 background modes + transparency slider are W10M Settings > Personalization > Start items.
- Decision: Confirm Settings is not a phase but a permanent W10M-style Settings hub created in phase 1 (Start + theme page only) that each later phase extends with exactly its own page (Notifications & actions in 5, Keyboard in 6, …)? If instead the owner wants one Settings phase, phases 1-4 are QA'd with fixed accent/background — accept?

### B4. Shizuku yes/no is undecided and gates the action center's scope and the onboarding flow
- Claim: without Shizuku a non-root app cannot flip Wi-Fi, Bluetooth, mobile data or airplane mode; those W10M quick actions become Settings.Panel sheets. With Shizuku the owner re-pairs it via Wireless debugging after every reboot.
- Evidence: R2:258 "Decide early whether to require Shizuku for the rest."; R2:126 "without Shizuku, third-party apps cannot flip Wi-Fi/airplane/mobile-data directly on modern Android"; R2:113 "must be re-started after every reboot". PLAN.md never mentions Shizuku; A9 (PLAN.md:42) covers permissions, and Shizuku is not a permission.
- Decision: Shizuku in (direct toggles; owner re-pairs Shizuku after each reboot) or out (Wi-Fi/Bluetooth/data/airplane quick actions open the Android panel sheet instead of toggling)?

### B5. R2 proposes v1→v2 swaps in four places; the split must not inherit them, and one of them hinges on an unlisted feature (wake word)
- Claim: R2's picks violate Rule 16 as written, and the STT choice depends on whether "Hey Cortana" is in scope — which the feature list does not say.
- Evidence: R2:223 "v1 = Vosk small-en + grammar … and platform TextToSpeech for replies; v2 = sherpa-onnx (Apache-2.0) for hotword KWS + Kokoro TTS" vs R2:201 "Pick Vosk (5.1) or this, not both"; R2:260 "shipping a Snygg theme first (zero fork) and only forking if the theme engine cannot reach the W10M look"; R2:42 "pin the version and be ready to vendor the ~15 files"; PLAN.md:38-41 (A7) every Cortana layer is permanent; PLAN.md:60 Cortana feature line has no wake word; PLAN.md:46-47 (A8) the feature list is complete. sherpa-onnx is the only candidate of the two with keyword spotting (R2:200).
- Decision: Is an always-listening "Hey Cortana" wake word in the plan? (Yes → phase 4's permanent runtime must be sherpa-onnx and phase 9 adds nothing to the audio stack; no → Vosk grammar is enough and hotword never comes.) The split must record one STT runtime, one TTS engine and one keyboard route (theme or fork) as permanent at the phase that introduces each.

### B6. Onboarding / permission-granting flow is not a part, and the install path decides whether Android's restricted-settings block applies
- Claim: the shell needs HOME, DIALER, SMS, ASSISTANT roles, notification access, accessibility, draw-over-apps, IME enable+select, battery-optimization exemption and Samsung "Never sleeping apps" — none of which has a place in the build order. On Android 13+ an APK installed by tapping the file is blocked from enabling accessibility and notification access until the owner uses App info > "Allow restricted settings"; an adb-installed APK is not flagged.
- Evidence: PLAN.md:49-60 and :78-89 contain no onboarding/permissions item; PLAN.md:42 (A9) is willingness, not a flow; PLAN.md:13 "load it on my phone via apk" (path unspecified). Restricted settings applies to non-session installs and not to session-based/adb installs: https://www.esper.io/blog/android-13-sideloading-restriction-harder-malware-abuse-accessibility-apis ; https://cleanbrowsing.org/support/mobile/disable-restricted-settings-android ("reinstall it by tapping the APK file … not via ADB"). Samsung sleeping-apps: https://dontkillmyapp.com/samsung ; Samsung re-adds apps to sleep lists after updates: https://us.community.samsung.com/t5/Fold-Flip-Phones/Device-care-auto-deep-sleep-apps/td-p/3378237.
- Decision: How does the APK reach the phone — adb over USB/Wireless debugging (no restricted-settings block; same channel Shizuku needs) or copying the file and tapping it (restricted-settings unlock step in onboarding)? And confirm the onboarding checklist is a phase-1 part (HOME role + status of every grant) that each later phase extends with its own row.

### B7. "Launch real apps with the transition" (phase 1) is half infeasible and half undefined
- Claim: the tiles-leaving-Start half is ours; the app window's entrance can be requested with a custom activity animation (unverified on One UI 8 with Android 12+ splash screens; QA on phone); the return-to-Start animation under gesture navigation is drawn by One UI Home's recents module and cannot be ours. R1 found no W10M spec for the shell launch animation at all.
- Evidence: PLAN.md:79 "launch real apps with the transition"; R1:136 "W10M shell Start→app launch animation (tiles fly out / turnstile) | NOT FOUND"; "Gesture navigation and Android's recents screen … are always controlled by a submodule of the pre-installed launcher, not by third-party launchers." (https://help.niagaralauncher.app/article/7-gesture-navigation); Samsung third-party launcher gesture history: https://www.androidpolice.com/5-years-later-custom-launchers-are-still-a-mess-with-gesture-navigation/.
- Decision: Define "the transition" for phase 1 as R1 §3.2's turnstile numbers applied to (a) the tiles leaving Start and (b) the app window entering, with the return-to-Start animation accepted as Samsung's generic one (NEEDS-HUMAN accept) — and which navigation mode (gesture or 3-button) is the fixed QA precondition on the phone?

### B8. No policy for the values R1 marked NOT FOUND — and R2's substitute timings are not W10M
- Claim: the split will need numbers for flip/peek/cycle durations, stagger rule, W10M gutter/edge, label size, transparency default, parallax rate, action-center grid, volume panel, glance clock layout, Cortana ring geometry/frames. R2 offers MetroLauncherAndroid's timings as "the best existing description of W10M live-tile timing" — they are one hobbyist's guesses with no source. The only primary Cortana artefacts R1 found are Microsoft GIFs inside a WP8.1 DLL.
- Evidence: R1:94 "Flip / peek / cycle durations (ms) | NOT FOUND"; R1:39, :72, :76, :94-96, :282, :296, :306, :320 all NOT FOUND; R2:50 "playFlipAnimation() 700 ms … slide 350 ms … wide/large cycle messages every 6 s"; R2:93 "copy live-tile timings … from MetroLauncherAndroid"; R1:320 "The WP8.1 GIFs in PersonaAssets720x1280.dll are the only primary artefacts identified".
- Decision: For every NOT FOUND value, does the owner (a) accept agent-chosen values (R2's timings included, labelled as guesses) that he vets on the phone as NEEDS-HUMAN rows, or (b) supply reference material first (his own W10M video/screenshots, a Lumia, or a firmware image to pull the Cortana persona assets from — the last one is copying Microsoft assets into the branding module)?

## MAJOR

### M1. R1's 150-epx medium tile cannot fit the 3-column W10M layout; tile size must be derived from column count
- Claim: 3 × 150 = 450 epx > 360 epx canvas. The UWP value only fits the 2-column mode: 2×150 + 12 gutter + 2×24 edge = 360 [derived]. In 3-column mode the medium tile is ≈100-104 epx. The split must define tile size = f(columns, canvas width, gutter, edge), not a constant.
- Evidence: R1:28 "medium 150x150"; R1:47 "≥5\" → 6-column (3 medium) layout"; R1:49 "Lumia 950 default | three-column layout"; R1:342 "360x640 … epx"; R1:39 gutter/edge NOT FOUND. Feeds B1's third question. No separate owner question.

### M2. MangoTile's motion values contradict R1's sourced numbers and its API cannot express them; adopting it for motion now means replacing it later (Rule 16)
- Claim: R2 recommends MangoTile for tilt/turnstile; its tilt is 10° + scale 0.94 with no depression or return delay, while R1's sourced tilt is 17.2° max, 25 px depression, 200 ms delay + 100 ms linear return. Write the motion primitives in-house from R1 (R2 itself says the flip is "a few lines"); use MangoTile at most for LongListSelector/Pivot.
- Evidence: R2:38 "metroTilt(interactionSource, maxTiltDegrees=10f, pressedScale=0.94f)"; R1:106-108 "MaxAngle = 0.3 rad (≈17.2°)", "MaxDepression = 25 px", "TiltReturnAnimationDelay = 200 ms, TiltReturnAnimationDuration = 100 ms, linear"; R2:42 "be ready to vendor the ~15 files"; R2:90 "covers it in a few lines". Repo verified live (MIT, 3 stars, created 2026-07-27: https://api.github.com/repos/Diffechento/MangoTile). No owner question; the split should encode "motion from R1, no motion dependency".

### M3. The app switcher stays Samsung's — missing from the CANNOT list
- Claim: a third-party launcher cannot supply the recents/task switcher without root; W10M's task view (long-press Back) is not buildable, and PLAN.md's limits list omits it.
- Evidence: PLAN.md:72 "Apps CANNOT fully replace: the real lock screen security, the status bar, system permission dialogs, or Samsung's own settings pages." (recents absent); Niagara quote under B7.
- Decision: Accept that the app switcher is One UI's, add it to the CANNOT list, and treat it as a NEEDS-HUMAN "feels like W10M" caveat?

### M4. System bars on Start are undecided
- Claim: Samsung's status bar and nav bar show over every app; on Start the launcher can hide both and draw W10M-style ones (clock/battery/signal; back/Windows/search) — only there. The plan neither chooses nor specs it, and R1 has no status-bar row.
- Evidence: PLAN.md:72-74; R1 has no status bar section.
- Decision: On Start, hide Samsung's bars and draw W10M-style status + nav bars (Samsung's remain inside other apps), or keep Samsung's bars visible everywhere?

### M5. Action-center gesture: replacing the system shade everywhere vs on Start only
- Claim: the status-bar swipe-down is consumed by SystemUI; to own it inside other apps the accessibility overlay must keep a permanent touch strip over the status-bar edge (TYPE_ACCESSIBILITY_OVERLAY sits above the status-bar layer — unverified; QA on phone), which then blocks Samsung's shade everywhere and interferes with apps using the top edge; the system shade would only be reachable via performGlobalAction(GLOBAL_ACTION_NOTIFICATIONS). On Start alone, the gesture is trivially ours.
- Evidence: PLAN.md:58 "W10M action center (pull-down overlay)"; R1:276 "swipe down from the top of the screen"; R2:126 toggles are a mix of direct calls and Settings.Panel intents; R2:122 no OSS no-root shade replacement found.
- Decision: Does the W10M action center replace the system shade everywhere (always-on top-edge strip, Samsung shade only via fallback) or only on Start (inside apps the Samsung shade stays)?

### M6. Glance ≠ Samsung AOD; the only no-root route keeps the panel on
- Claim: a non-root app cannot draw on Samsung's AOD. "Glance" can only be our black overlay/showWhenLocked screen kept alive after screen-off (owner turns Samsung AOD off; battery, burn-in mitigation, proximity/pocket handling, under-display fingerprint and Samsung lock screen underneath all become phase-8 edge cases; Android 14+ background-activity-launch rules for showing a screen from a service must be verified on phone). R2 missed the reference implementation of exactly this approach.
- Evidence: PLAN.md:58 "glance screen", :71 "glance/lock-style screen", :87 "8. Glance screen"; R2:263 "Treat as design work (lock-screen showWhenLocked activity or overlay)"; rosenpin/always-on-amoled exists — archived 2024-06-25, no license, 137 stars, "The original Always On Display for Android" (https://api.github.com/repos/rosenpin/AlwaysOnDisplayAmoled) — reference only.
- Decision: Accept glance = our overlay keeping the display on at minimum brightness with Samsung AOD turned off, or drop glance and keep Samsung's AOD?

### M7. Taking the SMS role loses RCS on the daily phone, and RCS must be turned off first or messages go missing
- Claim: no third-party SMS app gets RCS; Google says switching apps with RCS on risks not receiving messages, and toggling RCS repeatedly gets numbers blocked. Phase 7 needs a "turn off RCS chats in Google Messages" precondition and an owner acceptance.
- Evidence: PLAN.md:59 "messaging (default SMS role)"; "If you switch to another message app, you risk not receiving your messages" — https://support.google.com/messages/answer/9487020 ; https://www.androidpolice.com/enable-disable-rcs-chat-android/.
- Decision: Accept losing RCS (group chats, read receipts, high-res media) on the S25U when the W10M messaging app becomes default SMS?

### M8. Side-key assistant is "possibly" and stays unproven until phone QA; not testable on the emulator
- Claim: One UI 7+ lets the side-button long-press open "compatible third-party assistant apps", but Samsung's own example was broken at launch; whether a home-grown VoiceInteractionService appears in that menu is a phone-only QA row. Fallback that the assistant role does control: the corner-swipe assist gesture / home long-press.
- Evidence: PLAN.md:61 "possibly registered as Samsung's default assistant (side-key long-press)"; "You can set it to open Bixby or other compatible third-party assistant apps like Alexa (but Alexa doesn't work right now)." (https://www.sammobile.com/news/galaxy-s25-side-button-options-one-ui-7/); Samsung: https://www.samsung.com/us/support/answer/ANS10001575/. If B5 puts a wake word in: a microphone foreground service cannot be started from BOOT_COMPLETED on targetSdk 34+ (https://developer.android.com/develop/background-work/services/fgs/changes) — the home activity must start it after boot.
- No owner question; the split marks it phone-only with the fallback trigger named.

### M9. Service liveness and crash recovery are unplanned
- Claim: the action center, volume panel, live tiles and hotword all live in bound/foreground services that Samsung's sleeping-apps policy can kill or disable and that a firmware update can re-restrict; if the launcher crash-loops Android falls back to One UI Home. There is no health indicator and no per-phase edge case for "reboot / 24 h idle / Device care optimise / firmware update / service disabled".
- Evidence: https://dontkillmyapp.com/samsung ; Samsung community thread under B6; PLAN.md has no liveness/recovery item. Rule 5 requires the edge cases.
- No owner question; the split adds a liveness row to the onboarding part (B6) and the edge cases to phases 3, 4, 5, 8.

### M10. Single APK vs R2's install-another-app routes
- Claim: Q1 says "the same APK"; R2 offers routes that require the owner to install FlorisBoard or HayaiTTS separately, or ship dialer/SMS as separate GPL APKs.
- Evidence: PLAN.md:93 "sideload the same APK"; R2:137 "(a) ship a Snygg theme/extension that restyles stock FlorisBoard … user installs FlorisBoard"; R2:219 "simply let users install it and call android.speech.tts.TextToSpeech"; R2:163 "(3) ship the dialer/SMS as separate GPL APKs".
- Decision: Confirm one APK holds every part (launcher, overlays, IME, dialer, SMS, assistant) and no part depends on a separately installed app?

### M11. Phone-only QA is not enumerated; the emulator cannot exercise most Samsung risks
- Claim: restricted settings, sleeping apps, side key, One UI gesture animations, AOD/glance, fingerprint/lock-screen interplay, RCS, shade interception, Shizuku pairing and Screen zoom/resolution all exist only on the phone; the emulator can do roles, notification access, accessibility, overlays and simulated calls/SMS (`gsm call`, `sms send`). Rule 4 needs each phase to say which rows run where.
- Evidence: PLAN.md:92-93 "Develop against the Android emulator … then sideload"; B1, B6, B7, M6, M7, M8 above.
- No owner question; the split gives every phase an "emulator" and a "phone-only" QA list.

### M12. Start layout persistence, backup and app-change handling are not in the feature list
- Claim: the Start layout becomes the owner's daily data from phase 1; nothing says it survives reinstall/uninstall/factory reset, or what happens to tiles when an app is uninstalled/updated (LauncherApps callbacks). A8 says the feature list is complete, so this needs an owner add.
- Evidence: PLAN.md:49-60 (no persistence/backup/app-change line); PLAN.md:46-47 (A8).
- Decision: Add Start-layout export/import (a file the owner can copy off the phone) and uninstall/update handling to the feature list — in phase 1 (first layout exists) or phase 2 (edit mode makes it worth keeping)?

### m9. IME on the lock screen
- With a password (not PIN) lock, the keyguard uses the default IME; a phase-6 edge case is "our IME crashes on the keyguard" and the Android IME switcher on the lock screen is the recovery path (unverified; QA on phone).
