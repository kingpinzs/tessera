## The rule as built

`UriAccessRules.launchGrant(access, uri, mode)` admits only when ALL hold: a plain library address (`content`, no `@`
/ `%` in the authority, a path of `[A-Za-z0-9._~/-]`, a `forceUriPermissions` provider); the launch intent carries that
mode's grant flag; the URI's exact text is the launch's data or in its ClipData; the shell holds an explicit grant of
that mode for that text; and no persisted grant of the shell's covers it. Read: `helperMayRead` = the existing
`starterMayRead`, then the launch grant (the viewer and the player; Clock keeps `starterMayRead` unchanged). Write:
`captureMayWrite`'s (d2) on API 35+ = the launch answer OR the launch grant; (d1) unchanged.

| | API 34 | API 35 / 36 |
|---|---|---|
| Read (viewer, player) | the launch grant alone | the launch answer, then the launch grant |
| Write (capture) | still refused ((d1) cannot be asked) | (d1) AND ((d2) launch answer OR launch grant) |

## THE GAP (the builder's Risk 1; it does not fail closed there)

An app that cannot read X can still be admitted: a start path with no grant check (`startNextMatchingActivity`, F11)
plus a non-persisted grant the shell ALREADY holds for exactly X's text, which the shell cannot tell from this
launch's (F10). The likeliest source of such a grant: another live viewer, player or capture of the shell opened on X.
Effect: X shown read-only / played in the attacker's task; a capture still needs (d1); on API 34 a system or root
starter hitting a stale grant is admitted the same way. For the adversarial review to adjudicate and, if it can, close.
