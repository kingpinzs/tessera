# L13-7 fix — Reviewer A (design and correctness), 2026-09-27

Fix: 54ecf613 (`StartActivity.onWindowFocusChanged`). QA: 6bf35f14. Read-only review: code on main, the row driver, and
the evidence as committed. I did not read review-b.

## Verdict: FAIL

Window focus is the right signal, and the entrance half of the fix is correct: it cannot play twice, and it does not
change how Start comes back from an ordinary launch. But Start's comeback now has two triggers, and only one of them
does the whole comeback. That is a partial fix at the producer, and the QA's own evidence shows the effect. A small
amendment closes it.

## Blocking findings

**A1. The focus path plays the entrance but skips the rest of Start's comeback. The skipped work then lands at a wrong
moment, or never.**
- Path: `app/src/main/kotlin/app/tileshell/StartActivity.kt`, `onWindowFocusChanged` (lines 473–481) against `onResume`
  (lines 452–458). `launchApp` records the Tess tile's use and sets `pendingRecent` (lines 327–338). Its comment says
  both are "APPLIED on the way back, in onResume ... the tile must not leave the grid under the finger", and `onResume`
  says "Applied as Start COMES BACK, never while it is on screen". The new path consumes `returningFromLaunch`, plays the
  entrance, and leaves `pendingRecent` and `applyAutoSize` for whatever `onResume` comes next.
- Failure scenario, from the committed evidence (`qa/phase-13/L13_7-7f00cb9e/`):
  1. Tap the Tess tile, then press Back. Start comes back through the focus path, and the Tess tile stays in the grid:
     `back-1.xml` and `back-1.png` show it at `[9,1151]`. No `last open app: shell:cortana promoted` line appears in
     `back-slice.txt`. Compare `ctl-slice.txt`, where Settings is promoted in `onResume`.
  2. The next Home press, with Start already on screen, pauses and resumes Start (see `ring-launcher.txt` lines 50–51:
     `[bars] StartActivity` then `home: page 0`). That `onResume` applies the stale `pendingRecent`, so the Tess tile
     jumps to the row above the bottom row (`drawn-back-0.xml`: `[9,1579]`) on a visible Start, with no entrance. Turning
     the screen back on does the same. Auto-size is on by default (`ShellSettings.autoSizeTiles = true`), and the Tess
     tile's score rises with every tap (`[layout] use shell:cortana -> 6.6 / 7.6 / 8.6`). Its resize also waits for that
     same `onResume`, so a tile can change size on a visible Start. This is exactly what the code rules out.
  3. If the user taps another tile before any `onResume`, `pendingRecent` is overwritten and the Tess tile is never
     promoted, although the 2026-09-21 item 7 rule covers every tile launch, shell tiles included (Settings is
     promoted).
- Before the fix, this could not happen. Start was black, so the only way back was Home, and that `onResume` ran the
  entrance, the promotion and auto-size together (`L13_7-before-ad784939/drawn-back-0.xml` is the same `[9,1579]`, taken
  under an entrance).
- Fix, within scope: make the comeback one routine. Whichever of `onResume` or focus-back consumes `returningFromLaunch`
  first applies auto-size and `pendingRecent`, then plays the entrance, in the same order `onResume` uses today. The
  unconditional auto-size and `SlotDefaults.refresh` in `onResume` can stay as they are.
- Add to `l13_7_row.sh`: after each Tess case, the Tess tile is in the recent row. As written, the row cannot catch this.

## Notes (non-blocking), one per path in the brief

- **Is focus the right signal?** Yes. The Tess session is a separate window (type 2031, `FLAG_NOT_FOCUSABLE` not set,
  per the slice). It takes focus without pausing Start and hands focus back when it hides, and the before run's
  `Start has focus again` PASS shows that happens on the unfixed build. Android documents `onWindowFocusChanged` as the
  best indicator that the activity is visible, and it also covers any other launch that turns out to be a window over
  Start. The `returningFromLaunch` flag gates it, so ordinary focus traffic does nothing.
- **Ordinary launch.** The flag is set in `launchApp` on the main thread while Start holds focus. The next focus event is
  `false`, when the app takes focus. On return, `onResume` consumes the flag, and the focus return that follows sees
  `false`. Android does not guarantee `onResume` runs before focus, but both paths check and clear the same flag, so
  either order gives exactly one entrance (`ctl-slice.txt`: one `start entrance`). The one difference if focus came
  first: the entrance would start before `onResume`'s promotion and auto-size. A1's single routine removes that too.
- **Tess, then an app from inside Tess** (`ActionLayer.openApp` → `host.launchApp`, `close = true`). The app starts
  before the session hides after "Opening X", so Start is paused and never focused in between. On return, `onResume`
  plays the entrance and promotes the Tess tile. Correct. The step-aside path (`SessionResultRegistry`: start, then
  `setUiEnabled(false)`) and `requestMicrophone` (`hide()`, then `startActivity`) can hand Start focus for a moment
  first. The entrance may then play just before the page covers Start, and the later `onResume` plays none. Start still
  ends fully drawn, never black and never twice. At worst the user misses the entrance.
- **Failed launch.** No change for the worse. The failures that leave Start black are all older than this fix and none
  is L13-7's path: `SecondaryTiles.launch` returning false (`launchApp` ignores the result), the shell `no target`
  branch, and a `showSession` that silently shows nothing. The flag stays true and no focus change comes. The new path
  now rescues Start at the next focus return (for example, after the shade). `launchShortcut` already has the right
  pattern ("Nothing opened ... Come back now"). If the other three are wanted, they belong in their own ledger row.
- **Shade or system dialog over Start.** The flag is false unless a launch is in flight, so nothing happens. A shade
  pulled over Tess hands focus back to the session, not Start. A shade pulled during Start's exit lets the launch start
  under the shade, and focus then goes to the app. The flag is true while Start is on screen with focus only after a
  stale failed launch (above), and Start is black then anyway.
- **Satellite (phase 11).** `launchShortcut` sets the flag only after `startShortcut` returns `Ok`, on the main thread;
  a Failed plays the entrance at once with the flag false. No interaction.
- **Back on Start's back history.** `backOnStart` goes through `launchApp` as an ordinary launch: one entrance, in
  `onResume`. System Back inside Tess is taken by the session window, so it cannot reach Start's `backEvents` and start a
  back-history launch. The row's `Start has focus again` confirms nothing else opened.
- **Drawn Windows key.** In Tess, `goHome` starts HOME first and hides the session after. `onResume` plays the entrance
  and the focus return sees `false` (`drawn-windows-slice.txt`: `start entrance`, `session hidden`, `home: page 0`).
  Start's own drawn key only emits `homeEvents` and never touches the flag.
- **Can the entrance play twice?** No. The flag is set only by `launchApp` and by `launchShortcut` Ok, and consumed
  check-and-clear on the main thread by `onResume` or focus. An entrance from focus while an activity is taking over
  gets frozen by the paused frame clock and finishes on the next start, so Start comes back drawn.
- **`hideSystemBars` / `SetStartVisible`.** Neither needs the focus path. Start was never paused, and its requested bar
  visibility comes back into effect with focus (`back-1.png`: drawn bars, no system bars).
- **Phone.** The fix depends on the session window taking focus. On the emulator it does (`mCurrentFocus` =
  `VoiceInteractionSession`). The ledger's phone check on Jeremy's device is the only way to confirm that on the OEM
  build.
- **Evidence identity (lens B's call; noting only).** `L13_7-before-ad784939/L13_7.txt` names `apk built 7f00cb9e`, with
  `apk match NO` against installed `dfcd0c83`. The header does not say ad784939, which only the directory name and the
  README assert.
- **Commit message.** "fix tess tile issue" has no ledger ID; the KDoc carries it. Cosmetic only.
