## Checks

- **Root cause at the producer: agreed.** The window that covers the toast is the session's. No ring surface can sit
  above it: `TYPE_APPLICATION_OVERLAY` is the highest type a third-party app can add, and `VoiceInteractionService` has
  no hide call. One file, 17 lines, the shape of 0d74245 (`StartActivity.kt:174-183`).
- **drop(1) against the StateFlow's replay** (a collector always gets the current value first). *Already up:* the
  replayed ring is dropped, so Tess stays. *Ends:* `null`, removed by `filterNotNull`. *Superseded or a same-minute
  join:* a new non-null value, so she hides; right, another alarm fired. *Changes while up:* also hides her (note 2).
- **The job's lifetime.**
  - `doShow` sets `mWindowVisible` right after `onShow`, and `doHide` calls `onHide` only while visible. So every
    launch is paired with the cancel in `onHide`; `scope.cancel()` covers `onDestroy`.
  - A repeated `onShow` while visible (a second assist press) cancels the old job and relaunches it.
  - When `requestMicrophone` calls `hide()` from inside `onShow` (`open` with no RECORD_AUDIO), the job it launches
    is cancelled by the `onHide` posted afterwards.
  - Re-show of a reused session: `stop()` nulls `eventJob`, so `start()` rebinds; the new job gets a fresh drop(1).
    Code reading only: both sections of the row ran on fresh sessions (`session created` 19:45:35 and 19:46:18 in
    `ring-launcher.txt`).
- **Threading.**
  - The scope is `SupervisorJob + Dispatchers.Main.immediate` and `onShow` runs on the main looper, so `launch`
    subscribes synchronously. The replayed value is read and dropped before `onShow` returns; no ring can slip between.
  - RingService writes `_state` only on the main thread, so the collector resumes undispatched *inside*
    `_state.value = shown` (RingService.kt:177). The after-run shows the order: `full-screen intent: allow` .062,
    `a ring started` .062, `ring foreground` .064.
  - `hide()` is a synchronous binder call (`hideSessionFromSession`) that returns without re-entering RingService or
    the flow; `onHide` arrives later as a posted message (`session hidden` .129). Safe. It throws only before
    `onCreate` (`mToken` null), which cannot happen: the job starts in `onShow`.
  - Side effect: the hide runs on the ring's path before `startForeground` (about 2 ms), and so would anything added
    to this collector later.
- **What the hide drops.** *The reply:* `stop()` stops speech and cancels the event job; the late `final …
  audioMs=1000` at .148 is ignored, and the row shows no speech after the fire. *A pending card:* dropped, per H12;
  intended. *A photo draft while stepped aside:* note 1. Nothing leaks: `stop()` releases an earlier photo copy, and a
  late `attachPhoto` returns before it adopts the photo.
- **The lock screen.** The hide does not depend on the surface. Over the keyguard Tess always listens
  (CortanaModel.kt:140); a ring there resolves to LOCKED, and she hides before `startForeground` posts the full-screen
  intent, so `RingActivity` is not covered. Screen-off: the framework hides her already. Code reading only: the row
  drives only the in-use overlay.
- **No regression in Tess's own show and hide.** At open the replayed value is dropped, so the fix never hides her on
  show; in `onHide` the cancel runs before the existing body. E9 (not run) writes `ClockStore`, never
  `RingService._state`, so the collector does nothing on its path. The only change in Tess's own paths is note 1.
- **Should anything else also yield?** No, not for this defect. The shell's only other window above the overlay is its
  keyboard (`ime/KeyboardService.kt`, `TYPE_INPUT_METHOD`), at the bottom with the toast at the top, so Dismiss stays
  reachable. Tess's permission, unlock and result pages are activities, below the overlay. SystemUI's shade and
  heads-up are outside the shell's reach; glance (phase 07) is unbuilt.

## Notes (not blocking; for Jeremy's ruling or the ledger row)

1. **Stepped aside (L13-1): the hide is outside the defect and drops the draft.** While the photo picker is up,
   `setUiEnabled(false)` has already hidden Tess's window, so the toast is *not* covered; the investigation's premise
   ("a covered toast") does not apply.
   - Scenario: the user taps Add a photo on a reminder card and Tess steps aside. An alarm fires; the collector calls
     `hide()` and `stop()` wipes the card and the pending reminder. The user dismisses the ring and picks a photo:
     `attachPhoto` logs "photo picked with no reminder pending; dropped", `comeBack` sets the UI flag on a hidden
     session, and the user lands on Start with the reminder gone.
   - This contradicts L13-1's rule "Stepping aside is not closing" (`SessionResultRegistry.kt:19-21`). Pre-fix, the
     toast rang over the picker and the card survived. (Home during a step-aside already drops the card via the
     default `onCloseSystemDialogs`, so the state is not new; the trigger is.)
   - Not blocking: the alternative needs a come-back rule the doc lacks (skip the hide while stepped aside, and in
     `comeBack` hide if `RingService.state.value != null`). The investigation records this; the row and commit don't.
2. **"A new ring" is really "any new non-null value".** `present()` re-publishes the *same* ring with another surface on
   `ACTION_SCREEN_OFF` / `ACTION_USER_PRESENT` (RingService.kt:213-217, 176-177). That closes a Tess opened over the
   ring, which the comment at CortanaSession.kt:215-216 and the ledger row say does not happen, and logs "a ring
   started" wrongly. Screen-off is harmless (the framework hides her anyway).
   - Scenario: Tess is opened over the locked toast and her Unlock card is used. The keyguard is dismissed, sending
     `USER_PRESENT`; `present()` moves the ring to OVERLAY; Tess hides, `stop()` drops the `Pending.Locked` request, and
     `onUnlocked` logs "unlocked with nothing pending".
   - Rare. If "new ring" is the intent, key the collector on `ids` (map to `it?.ids`, `distinctUntilChanged()` ahead
     of `drop(1)`); otherwise correct the comment and the row.
3. **drop(1) cannot tell "opened over a ring" from "a ring a moment before the window".** If the alarm's
   `onStartCommand` reaches the main looper before `onShow` (a few hundred ms after an assist press), the new ring
   counts as already up. A held press, or any open over the keyguard, then leaves Tess listening over the toast.
4. **The mic-grant reopen.** `CortanaPermissionActivity` (EXTRA_REOPEN_LISTENING) re-shows Tess listening after the
   grant. If a ring started while she was hidden for the prompt, she reopens over the ringing toast: under drop(1),
   "opened over a ring", though the user opened her before it rang. Narrow.
5. **drop(1) is unruled.** Tess has no voice snooze or dismiss (nothing in `cortana/` sends `ACTION_SNOOZE` or
   `ACTION_DISMISS`), so a Tess opened over a ring covers the only Snooze and Dismiss until Back. The investigation left
   it to Jeremy; "All 3" approved the fix, not this choice.
6. **Rests on code alone:** the lock screen, the step-aside, a reused-session re-show after a ring-hide, the surface
   move, and E9. The row covers only the in-use overlay, with Tess listening and with Tess idle.
