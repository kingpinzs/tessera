## What I checked and found right

1. **The precedence is exactly the ruling.** `TileSourcePrecedence.resolve` (LiveTileEngine.kt:21-27): playing MUSIC → API → NOTIFICATIONS → MUSIC (whatever is left, i.e. paused). `playing()` (:19) reads the front face's `NowPlaying.playing`. MusicFeed publishes `front = face` iff `plan.front` (MusicFeed.kt:179), and `MusicRules.plan` sets `front = true` iff `now.playing` (MusicRules.kt:90), where `now.playing` is `isPlaying(state)` = PLAYING or BUFFERING (MusicRules.kt:53-54, MusicFeed.kt:133). So "playing" in the engine ⇔ "playing" in the feed, BUFFERING included, and a paused publish is `faces = [face]`, `front = null` (MusicFeed.kt:175, :179), which `playing()` rejects. An app that plays nothing has only API and NOTIFICATIONS slots and gets phase 01's rule unchanged (phase-01-start-live-tiles.md:59).
2. **Pause → stop → destroy leaves the paused face, as item 3 rules.** Pause/stop: `isPlaying` false → plan flip, no front, no controls, no growth (MusicRules.kt:91) → MUSIC slot = paused face, lowest precedence. Session destroyed: `onSessionDestroyed` republishes without it (MusicFeed.kt:84-89) → `pick` null → `next = published.copy(playing = false)` (:138) → same paused face (or no republish when already paused, :139). It sits behind API and notifications and flips behind the logo when nothing else has content; the transport strip goes on pause (INDEX Change Log 2026-09-22 "ITEM 3's PAUSE BEHAVIOUR STANDS"). The only gap is F-2 (uninstall).
3. **No writer of a bare `pkg:<package>` bypasses the arbiter.** `grep -rn 'LiveTileEngine.publish(' app/src/main`: PhotosFeed.kt:94/:119/:178 (`PHOTOS`), CalendarFeed.kt:87 (`CALENDAR`), WeatherFeed.kt:215 (`WEATHER`), LiveTileStore.kt:202/:381/:407/:473 (`secondaryContentKey`, i.e. `pkg:<p>#<id>`, still through `publish()` as required). `packageKey(` callers: StartPage.kt:155/:178/:235/:237 (reads), LiveTileStore.kt:745 (builds the secondary key), LiveTileEngine.kt:66 (inside `publishPackage`). All three producers use `publishPackage`: MusicFeed.kt:160/:171/:196 (MUSIC), TileNotificationListener.kt:83 (NOTIFICATIONS), LiveTileStore.kt:198/:472 (API). No test writes a `pkg:` key through `publish()` (`grep packageKey\|"pkg:" app/src/test` → the new test only).
4. **`previewOwners` did nothing that the slots do not do now.** Its three sites: the listener's early return (replaced by the engine's order); `wipeLocked` (LiveTileStore.kt:197-198: API null, unconditional — the same outcome for a package that had API content, a no-op for one that did not); `republishTileLocked` (:466-475: always `publishPackage(API, content)`, where the old three-way branch was only idempotence bookkeeping). Consumers: `LiveTileSettings.setDisabled` (LiveTileSettings.kt:54 → `republish`) and `setApiEnabled` (:24 → `republishAll`) both end in `republishTileLocked` with `disabled = true` → API null → notifications or a session show; uninstall → `onPackageRemoved` → `wipeLocked`; identity change → `checkIdentityLocked` → `wipeLocked`. One behaviour change, inside the ruling: a notification preview now returns the instant the API queue clears or is disabled, instead of at the next notification event or rescan; row (a) of the gate asserts it ("clearing the queue lets the notification show", qa/phase-11/L11-1/L11-1.txt).
5. **Adversarial (API trust surface).** No app can write another app's slot: the API path keys on `ContentProvider.getCallingPackage()` (phase-01 Decision :60, LiveTileProvider → `LiveTileStore.update(pkg, …)`), the notification path on `sbn.packageName` (TileNotificationListener.kt:38/:43/:72), the music path on `MediaController.packageName` (MusicFeed.kt:126) — all system-attested. An app can suppress only its OWN lower sources (its playing session over its own queue and notifications), which is the ruling. Per-source slots mean a null from one producer can no longer clear another's content (the L11-1 mechanism, TileSourcePrecedenceTest `notificationNullsNoLongerWipeAPlayingFace`). Kill switch, master switch and wipe clear the API slot and the API badge (LiveTileStore.kt:466-476, :197-199) — not other apps', not other sources'. The one "slot never cleared" is F-2 (MUSIC after uninstall), not exploitable by a third party. Thread safety: `publishPackage` and `publish` are both `@Synchronized` on the one `LiveTileEngine` object (:60, :78); `packageSources` is touched only inside them; the `state` read-modify-write happens under the lock (:67-69), so the listener's binder thread, MusicFeed on the main looper and the store's `livetile` handler thread serialise correctly; the store takes its own `lock` then the engine's, the engine calls out to nothing but `Diagnostics`, so there is no lock-order cycle. `TileSourcePrecedence` is pure.
