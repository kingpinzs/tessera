# L11-1 — fix plan (one arbiter for a package's tile content)

Ruling: Jeremy, 2026-09-24, "(a)" — the precedence between a playing song, the Live Tile API and notifications lives in
the tile engine, in one place. Owner parts: phase 01 (Live Tile engine, notification feed, Live Tile API store) and phase
10 (MusicFeed's tile rule). Found by phase 11's gate; blocks phase 11 E10 (resume point: E10's control sub-step).

## The defect

`LiveTileEngine` holds ONE content slot per package (`pkg:<package>`) and three producers write it:
`MusicFeed` (the now-playing face — since phase 10 build task 5, `49937f6`, which moved it off the Music slot's own
`feed:music` key), `TileNotificationListener.rebuild()` (notification previews, or null when the app has no eligible
notification) and `LiveTileStore` (the Live Tile API queue). The only precedence is a one-off check in the notification
feed (`previewOwners`: the API queue wins over notifications). Music has none, so every media-notification update
republishes the slot as null and wipes the playing tile's face and transport strip. Evidence: qa/phase-11/E10/
(`l11-1-sequence.txt`, Fossify: the face 4×, null 5×). Jeremy's phone sign-off of the strip (09-22 04:48, `e181529`)
predates the re-key (09-22 09:17), so it ran on the old key.

## The fix

1. **`LiveTileEngine` keeps each producer's content for a package separately** —
   `publishPackage(pkg, source, content)` with `source` ∈ {MUSIC, API, NOTIFICATIONS} — and the visible `pkg:<package>`
   entry is `TileSourcePrecedence.resolve(...)`, a pure function:
   **a playing session's face (MUSIC with a front face) > the API queue > notifications > a paused track's face (MUSIC
   with no front face).** This extends phase 01's rule ("preview = the API queue if the app uses it, else notifications")
   by one source at each end; it changes nothing for an app that plays nothing. `publish(key, …)` stays for the non-package
   keys (`feed:*`, secondary tiles).
2. **The three producers publish their own source**: `MusicFeed` → MUSIC (its clears too); `TileNotificationListener` →
   NOTIFICATIONS, and its `previewOwners` early return goes (the engine now decides); `LiveTileStore` → API for a primary
   tile (queue content, a cleared queue, a wipe). Badges are untouched (BadgeStore already has its own precedence).
3. **One diagnostics line per publish says what shows**: `[engine] publish pkg:<p> source=<s> … -> shows <winner>`, so a
   ring slice proves which source won.
