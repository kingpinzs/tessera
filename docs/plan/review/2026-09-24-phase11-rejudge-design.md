## What I checked and found right

1. **The ruling is implemented exactly, in one place.** `TileSourcePrecedence.resolve` (LiveTileEngine.kt:22-28) checks, in order: a playing MUSIC (`playing()` at :20 means a front `NowPlaying` whose `playing` is true), then API, then NOTIFICATIONS, then MUSIC whatever is left (the paused face). MusicFeed sets `front` if and only if `plan.front` (MusicFeed.kt:182), and `plan.front` if and only if `now.playing` (MusicRules.kt:90), BUFFERING included (MusicRules.kt:53-54). So the engine's "playing" and the feed's "playing" are the same state. The three producers publish only their own slot: MusicFeed.kt:163/:174/:208 (MUSIC), TileNotificationListener.kt:84-88 (NOTIFICATIONS), LiveTileStore.kt:473 (API; the secondary key at :474 stays on `publish()`). Nothing else writes a bare `pkg:` key (R1-3's grep). An app that plays nothing has only API and NOTIFICATIONS slots and gets phase 01's rule ("Preview content = the API queue if the app uses it, else notifications", phase-01-start-live-tiles.md:59) unchanged.
2. **7cb3742 resolves F-1 to F-5.**
   - F-1: the fix is at the consumer. `rescan` asks `LiveTileEngine.packages()` (TileNotificationListener.kt:55) instead of parsing keys, so `o#t` is never a "package". It is hardened in the engine too: `had` (LiveTileEngine.kt:88) means an unowned key is never removed (:95). Tested at TileSourcePrecedenceTest.kt:86-91.
   - F-2: `forgetPackage` (:73-81) is called from `wipeLocked` (LiveTileStore.kt:199), which runs for every non-replacing removal and every identity mismatch. MusicFeed drops its track (MusicFeed.kt:192-199). Tested at TileSourcePrecedenceTest.kt:94-108. The residual race is R1-1.
   - F-3: the `LiveTileStore` import is gone (TileNotificationListener.kt:3-14).

   - That makes 12 tests: 7 from ca73663 and 5 from 7cb3742, matching INDEX :59 and README.
3. **Threading.**
   - Every read and write of `packageSources` and `state` holds the engine object's monitor: `publishPackage` and `publish` are `@Synchronized` (:84, :105), `packages()` is `@Synchronized` (:61), and `forgetPackage` uses `synchronized(this)` (:74), the same monitor as the others.
   - The engine is called from the main looper (MusicFeed, whose callbacks are registered with a main-looper Handler at MusicFeed.kt:67-71 and :94), from the notification listener's callbacks, from the `livetile` thread (receiver posts) and from provider binder threads (LiveTileProvider.kt:86 → `checkIdentity`). All of these serialise on that monitor.
   - Forget listeners run outside the engine lock (:80), under the store's `lock` (`wipeLocked`). MusicFeed's listener only posts. So the lock order is store → engine, there is no cycle, and no callback runs under the engine lock.
   - `MusicFeed.forget` runs on main alongside every other access to MusicFeed's state.
   - The one ordering hole is R1-1.
4. **A forget racing a notification or API publish is benign.** A NOTIFICATIONS null for a forgotten package is a no-op (`had` = false). A rescan that snapshots `packages()` just before a forget can at most re-create a NOTIFICATIONS slot from a notification the system has not yet cancelled. The listener's `onNotificationRemoved` → `rebuild` → null then clears it (TileNotificationListener.kt:40-43). API publishes and wipes both run under the store's `lock`, so they cannot interleave.
5. **A package whose only content was a secondary tile.** Its owner `o` is never in `packageSources`. `forgetPackage(o)` finds no `pkg:o` and changes nothing (:75-77), and the wipe's own loop clears `pkg:o#<id>` and its badge (LiveTileStore.kt:202-205). A rescan never visits `o#t`, and a NOTIFICATIONS null for `o` cannot remove `pkg:o#t` or any other key it did not hold (:95).
6. **A reinstall inherits nothing** once both halves of the forget have run: every slot is dropped (:75-77) and MusicFeed's memory and growth are dropped (MusicFeed.kt:194-197). A later publish starts from nothing (TileSourcePrecedenceTest.kt:104-107). The exceptions are R1-1 (the window) and R1-4 (the new install's own content is cleared as well).
