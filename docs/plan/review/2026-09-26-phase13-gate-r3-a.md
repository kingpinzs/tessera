## Is 9c4d049f right?

- **Sharing: correct.** See above. The lock is short, never held across a suspension, and never taken in the reverse order, and the
  completion handler only removes its own entry (`SingleFlight.kt:17-21`). So there is no deadlock and no stale entry.
- **A cancelled waiter: correct.**
  - The run belongs to `CoroutineScope(SupervisorJob() + Dispatchers.IO)` (`BackgroundDecoder.kt:29`), so a caller's cancel ends only
    its own `await`.
  - For the static build, that `CancellationException` reaches `StaticBackdrop.build`'s rethrow (`ui/fluent/StaticBackdrop.kt:83-86`)

    `E1/slice-5-switch-on.txt`). No 0eb36905 row's ring or slice holds a `static backdrop failed` line outside E13.
- **A decode failure: correct.**

### NON-BLOCKING

**N1: a late `remember` from a superseded decode can evict the current picture's cache entry.** This is not new with 9c4d049f.
- `BackgroundDecoder.remember` stores whatever URI finishes, unconditionally (`start/BackgroundDecoder.kt:49`, `:53-56`). Now that
  a run outlives its callers, the old URI's decode completes after a change and overwrites the one-entry cache.
- If the new URI's decode finished first:
  - the cache holds the old picture until the next change;
  - the next `decode` of the new URI (for example `StaticBackdrop.ensure` when acrylic turns on) decodes it again, while Start keeps
    the first copy.
- The old code had the same ordering: its `remember` ran at the end of the same IO block, which cannot be cancelled.
- It needs a second change while the first decode is in flight. I found no route that does that: the picture is chosen in the separate
  Settings activity, one change per return.
- Fix, if wanted: `forgetAllBut` records the wanted URI, and `remember` stores only that URI.

**N2: EDGE_RAPID's back race. The Change Log's description does not match the kept runs.**

  instead".
