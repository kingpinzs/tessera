## The defect

- **Symptom.** With the app list's hold band open, a finger that goes down on the band's "Pin to Start" item and moves
  60 px sideways drags Start's pivot under the band: the `app_list` page's bounds go `[0,0][1080,2196]` →
  `[37,0][1080,2196]`, and on phase 13's builds the pivot logs a drag's settle on release (`[motion] pivot … settle=232`).
  E7(d) then cannot measure its M and A captures against U: the item and its lights draw on a page that moves.
- **Where.** The band (`PinToStartMenu`, `applist/AppListMenu.kt`) is composed inside the app list's page
  (`AppListPage.kt:322-344`, the overlay box over the list's rectangle), and that page is page 1 of Start's
  `HorizontalPager`. The band's scrim takes only a tap (`awaitFirstDown` → `waitForUpOrCancellation` → dismiss); its
  items consume only the down and the up (`MenuItem`: `awaitFirstDown().consume()`, then `waitForUpOrCancellation`).
  Nothing in the band consumes a MOVE, so the pager — the band's ancestor, which sees each event after its descendants —
  takes the unconsumed sideways moves as its own drag. The list itself does not scroll under the band: the overlay box is
  a sibling above it, and a sibling below the topmost hit takes no pointer input.
- **Same leak, second overlay (scope probe, this session).** The letter jump grid (X8, phase 01's part), drawn in the
  same overlay box, has the same shape (a scrim that takes only a tap) and the same leak. The band's scrim leaks too, not
  only its item. `qa/phase-13/scripts/l13_2_scope.sh` on apk 15aa7f5f (installed 20:01, the build of c73c32cf), row
  `qa/phase-13/L13-2-scope-current-15aa7f5f/`:
  - band scrim, DOWN 300 px below the band, MOVE +60: page `[0 0 1080 2196]` → `[37 0 1080 2196]`, LEAK yes; after UP
    the page settles back and the band is still open (the pager's drag cancelled the scrim's tap).
  - jump grid, DOWN 150 px above its bottom, MOVE +60: `[0 0 1080 2196]` → `[37 0 1080 2196]`, LEAK yes; after UP the
    grid is still open.
- Evidence: qa/phase-13/L13-2-pre13-1ee619f8/ (reproduced before phase 13), qa/phase-13/L13-2-current-15aa7f5f/ (driver

## Constraints the fix works inside (existing code and Decisions, not new rulings)

- E7(d)'s press contract (phase 13, FINAL): DOWN on the item → D; MOVE +60 px still inside the item → M, where the lights
  followed the finger (the press is still on); MOVE off the item → A, where the press has ended; UP outside the item runs
  nothing (no `pin to Start` line). The fix must keep the item pressed through a move inside it — so an item cannot simply
  cancel its press on the first move.
- The band is modal as built: a tap off it dismisses it, its items consume their taps so a pick is not also a tap outside
  (`AppListMenu.kt` KDoc), Back closes it (`AppListPage.kt:239`). The jump grid: a tap off a cell dismisses it, Back closes
  it (`:238`).
- Precedent for "hold the pivot still": edit mode sets the pager's `userScrollEnabled = !edit.active`
  (`StartActivity.kt:206`, "a drag across the screen moves a tile, not the pivot").
- Precedent for "draw above the pivot": the folder name box, the pin prompt and the slot picker are drawn in Start's own
  layer above the pager, "so focusing it cannot make the pager bring it into view" (`StartActivity.kt:220-243`).
- Phase 13 (T13-11): the band's acrylic records the app list page's backdrop layer; the overlays sit over the list's own
  rectangle so the band never records itself (`AppListPage.kt:193-194`).
- The Music band (E7(e)) is not under a pager and is not affected (ledger row).

## Rulings

- **Q1 (2026-09-25, Jeremy: "(A)") — where the modality is enforced: in the overlays themselves.** A gesture that
  starts on an open overlay (the band's items, the band's scrim, and whatever else Q2 puts in scope) has every one of its
  pointer changes consumed by that overlay, so no ancestor — Start's pager — can take it as a drag. The item keeps its own
  press: held while the finger stays on the item, ended when it leaves, nothing run on an UP outside (E7(d)). Start's
  pager is not changed. Known risk, stated when asked: if the pager's drag detector reads the pointer before its
  descendants do (the Initial pass), consuming at the overlay cannot stop it; the regression row proves or disproves
  this on the device before anything is claimed, and a disproof comes back to Jeremy. Rejected: (B) the pager holds
  still while an overlay is open (edit mode's `userScrollEnabled` switch) — a consumer-side patch every future overlay
  must remember to report to; (C) draw the overlays in Start's layer above the pager — rewires phase 13's acrylic
  backdrop and the anchors.
- **Q2 (2026-09-25, Jeremy: "(c)") — scope: the band, the jump grid, and every other overlay drawn inside a swipeable
  page.** The swipeable pages are Start's pivot (`StartActivity.kt:198`: page 0 Start, page 1 the app list) and Music's
  pivot (`MusicCollectionPage.kt:257`, `music_pivot`). Each overlay inside one of their pages is probed on the emulator the
  same way (DOWN on it, a sideways MOVE, the page's bounds read with the finger down) and, if it leaks, fixed with Q1's
  mechanism and covered by the regression row. The jump grid (phase 01's part) and any other owner's overlay get a line
  on their phase's row, as L13-1's fix did on row 03. Rejected: (A) the band and the jump grid only; (B) the band only,
  the jump grid on its own ledger row.

## The fix (agent, from Q1–Q2)

1. **One modal rule, one place.** A shared modifier in `ui/components` for an overlay's root (the scrim box): it consumes
   every pointer change of a gesture that starts on the overlay, in the Main pass — after the overlay's own items have
   seen it, before any ancestor does — so Start's pager and Music's pager see a consumed stream and cannot start a drag.
   A tap on the root off any item (down and up with no move past touch slop) runs the overlay's dismiss, as built; a
   drag on it runs nothing and leaves the overlay open (the agent call below).
2. **One press rule for the items inside those overlays** (the band's `MenuItem`, the app list's `JumpCellView`,
   Music's jump cells): pressed from DOWN while the finger stays on the item; ended for good when it leaves; a lift on
   the item runs it; a lift anywhere else runs nothing — E7(d)'s contract, which the band item already needs. The items
   track their own bounds instead of `waitForUpOrCancellation`, because that helper returns "cancelled" on a change
   anyone consumed (it looks again in the Final pass — Compose source as recalled; the build's first red run confirms),
   so with the root consuming every move it would cancel every item press on the first move. Music's cells use
   `clickable` today and move to this rule.
3. **Applied to:** `PinToStartMenu` (scrim and items, `applist/AppListMenu.kt`), the app list's `JumpGrid`
   (`applist/AppListPage.kt:605-630`), Music's `JumpGrid` (`music/MusicCollectionPage.kt:763-`). Both pagers are not
   changed (Q1).
4. **The lights are unaffected:** `revealLights` reads the Initial pass (`ui/fluent/RevealLights.kt:77-81`), before any
   Main-pass consumption, so they keep following the finger; E7(d)'s M capture on the fix's build proves it.
5. **Records:** after the fix, a line on rows 01, 02 and 10 (their docs are FINAL and not edited) and a Change Log
   entry, as L13-1's fix did on row 03.

## Found at build (agent, 2026-09-25)

- **Music's grid and cells kept what `clickable` gave them.** `clickable` carried a click action in the semantics (merging
  its descendants) and the press indication (`LocalIndication.current`); the root and the live cells keep both
  (`semantics(mergeDescendants = true) { onClick }`, `indication` fed by the press rule), so only the gesture changes.
- **A recomposition must not restart the rule mid-gesture.** A `pointerInput` keyed on a lambda restarts when its caller
  recomposes, and a restart mid-gesture would hand the rest of that gesture to the pivot; `modalOverlay` and
  `overlayItem` key on nothing and read their callbacks through `rememberUpdatedState` (the codebase's `revealLights`
  pattern).
- **Driver faults, kept:** the row's first pre-fix run (L13-2-row-before1-driver-cascade/) let (B4) and (J5) inherit the
  previous step's state — on the defect build (B3)/(J4) had already swung the pivot to Start, so "a tap off it closes it"
  tapped Start; both now open a fresh overlay, and the pre-fix run was repeated on the corrected blob. The repro's first
  after-fix run exited 126 (the script is committed without its executable bit, L13-2-after-fix-120e52ec/run1-not-executable/);
  run again through `bash`, unchanged.
