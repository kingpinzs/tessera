## Focus and keyboard for the name box while it is unplaced

- `OverlayLayer` changes placement only; the composition lifetime is unchanged. The field stays focused until the next
  frame's recomposition removes it, exactly as before the fix, when it stayed placed and focused for that frame.
- In 1.11.4, `FocusTargetNode` has no placement check: `onPlaced` only calls `focusTargetAvailable` behind a flag. Key
  events and IME commits therefore still go to the field for that frame, as they did before. No new window opens.
- The keyboard:
  - The first Back belongs to the IME, as the plan says.
  - The build targets SDK 36 (edge-to-edge) and there is no `imePadding` in music/, so the IME covers the drawn nav bar.
  - So a Back that reaches the page handler finds the keyboard already down. The name box's scrim is unplaced, so a
    touch in that frame reaches the page and cannot re-show the keyboard.
- `PopupLayout` has no placement check. A cursor-handle popup, which is a separate window, can outlive the box by one
  frame. That is cosmetic and no worse than before.

## Notes (non-blocking)

1. **The two Backs disagree in two places.** Both predate this fix and are outside L13-6's shape.
   - Now Playing's drawn Back (`MusicNowPlaying.kt:261`, `onBack = onBack`) leaves Now Playing while `more` is open.
     Hardware Back closes the band instead.
   - The collection's drawn Back has no branch for the jump grid, because `gridOpen` is local to `PivotPage`. With the
     grid open, it reaches `else -> onBack()` (`:321`), which is `finish()` (`MusicActivity.kt:132`).
   - Neither leaves a stale overlay: the whole page goes. Candidate ledger rows for Jeremy; not this fix.
2. **The drawn-Back branches are the first `dismissOverlay` calls from inside pointer dispatch** (the nav slot's
   `clickable` `onClick`).
   - They are safe. A `clickable` never fires on a removal's cancel, so the call is never reached from
     `Recomposer.applyChanges` (round 1 note 5's concern). The invalidation only requests a relayout, which the next
     MotionEvent's `measureAndLayout` applies before its hit test.
   - The probe sends only `keyevent 4`, so these two branches rest on code reading and on their being identical in
     form to the probed handler.
3. **The plain-write dismissals keep the one-message window** that L13-3 left on its overlays: `MusicMenu`'s tap-off
   and item picks, the name box's tap-off and IME Done. This is consistent with L13-3's triage (round 1 note 5), and
   the ledger defines L13-6 as the Back path. Accept.
4. **Page-level Backs** (`openPlaylist = null`, `detail = null`, MusicActivity's `screen = COLLECTION`) leave the old
   page placed for a frame. A touch there is misdirected rather than lost. That is a different shape, and out of scope.
5. **KDoc drift.** `OverlayLayer` (`ModalOverlay.kt:24`) and `LocalOverlayActive` (`:18`) still list only the app list's
   band and grid and Music's grid. They should now name Music's hold menu, the name box and Now Playing's band.
6. **The same shape outside music/, by code reading only.** `clock/AlarmTab.kt:224` closes a flyout on Back by writing
   `flyout = null`. `ClockFlyout` (`clock/ClockWidgets.kt:206-210`) has a full-screen scrim with its own `pointerInput`.
   This is not reproduced. It is a candidate ledger row, outside this defect's scope.
7. **Producer.** The layer wraps the overlays at their call sites, which own the state and the Back, as L13-3 did. It
   does not wrap them inside `MusicMenu` / `PlaylistNameBox`. That is the right place: those two are stateless, and
   `MusicPlaylistUi.kt` is untouched.
