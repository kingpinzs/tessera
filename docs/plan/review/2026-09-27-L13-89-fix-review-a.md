## Library facts this rests on (activity 1.13.0 bytecode)

- `ComponentActivity.getNavigationEventDispatcher()` is `onBackPressedDispatcher`'s own dispatcher. Compose `BackHandler`
  registers there (`LocalNavigationEventDispatcherOwner`), and `onBackPressedDispatcher.onBackPressed()` sends
  `backCompleted` into the same one, so the drawn Back reaches exactly the system Back's handlers.
- `NavigationEventProcessor.addHandler` uses `addFirst`: the handler registered last is asked first.
- `ActivityFlags.isOnBackPressedLifecycleOrderMaintained` is `true`. `BackHandler` adds its handler once, in a
  `DisposableEffect`, and toggles it with `LifecycleStartEffect`; the Clock's lifecycle-owner callback is added at
  `addCallback` and only toggled on START / STOP. So the order is registration order and survives stop / start.
- With nothing enabled, the fallback is `super.onBackPressed()` → `Activity.onBackPressed` → `ActivityClient.onBackPressed`.

Only the two cases the ledger names change, plus the root. The comment's order (grid, then the overlays, then leaving) is right.

**The root.** MusicActivity is a MAIN / LAUNCHER activity with its own `taskAffinity`, so it is its task's root. Since API 31
(minSdk 34), `ActivityClientController.onBackPressed` moves such a task to the back instead of finishing it. So the drawn
Back at the root now backgrounds Music: no `onDestroy`, no `MusicPlayer.release()`, pivot and scroll kept, and the next open
resumes it rather than creating it. The old code called `finish()`. The system Back and Windows (`goHome`) always did what
the new code does. Started as a non-root activity, the fallback still finishes. Case (4) drawn passes on the Android 16 emulator.

**Reliance on `finish()`: none found.** Each page has one caller, MusicActivity. The only code that depends on finishing is
`onDestroy`'s `if (isFinishing) MusicPlayer.release()`, which the system Back never reached either; MusicPlayer is a
process-wide singleton that `cortana/action/ActionLayer.kt:563` also connects, so not releasing it is the safer side. No
driver checks `MusicActivity created` or `controller released` after a Back. l13_8 case (4) asserts only that the UI is gone,
and `music_open` force-stops before each case.

## L13-9

- **Layout and placement: unchanged.** OverlayLayer is a loose-measured child of the ClockScaffold content Box. It takes the
  size of its largest child (the fillMaxSize scrim, so the content box), sits at TopStart, and places each child at (0,0)
  with the same loose constraints the Box gave. The scrim covers the same box; the Column keeps `offset(x, top)`. Draw and
  hit order are unchanged: the layer is where the `when` was, still under the app bar (`bar` is invoked after `content`).
- **BoxScope.** The three flyouts are `BoxScope.` extensions, bound inside the layer's lambda to the scaffold's outer scope.
  They and `ClockFlyout` use no BoxScope member; every `align` is on an inner Box or PressBox scope, so nothing is lost.
  Trap for later: an outer-scope `align` or `matchParentSize` would compile, but OverlayLayer ignores Box parent data.
- **The name field's Back.** One Back still clears `flyout` and `editingName`, as before; the flyout's part is now applied
  at once. `editingName` is a plain write, which is fine because the field has no scrim. With the keyboard up, the first
  system Back goes to the IME.
- **L13-3's rule.** `active` is read while placing. `dismissOverlay` is used only in the Back handler; the tap-off and items
  write plainly, never from `applyChanges` (amendment note 5).
- **Sounds page, music picker.** ClockScaffold with no bar and no overlay: nothing to fix.
