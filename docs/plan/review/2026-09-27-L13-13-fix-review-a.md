# L13-13 fix: review A (design and correctness), 2026-09-27

Reviewed: 2f7b5faa (the fix), 431f4c5c (the driver, L13_13.txt for both builds), `ui/components/ModalOverlay.kt`, the
L13-2 fix plan, the L13-11/12 review A, and foundation-android 1.11.4's bytecode (`javap`). Read-only: no build or adb.

## Verdict: FAIL

## Blocking findings

1. **`modalOverlay` breaks the city search's field, its result rows and its list scroll for a real finger.**
   (`clock/WorldClockTab.kt:233`, with `:239-256` and `clock/ClockWidgets.kt:193-207`)
   - How it happens: the root consumes every pointer change in the Main pass (`ModalOverlay.kt:84-90`). The children
     see each change first in Main, but three of them check for consumption again in the Final pass, and the root's
     consumption is visible there:
     - **Result rows** are `PressBox`, which uses `waitForUpOrCancellation`. In 1.11.4 that function awaits Final
       after Main and returns null on `isConsumed`, so a press is cancelled by any MOVE between down and up.
     - **The field** is the String `BasicTextField`, which goes through `CoreTextField`. Its tap is
       `tapPressTextFieldModifier`, then `detectTapAndPress`, then `waitForUpOrCancellation`. That tap re-shows the
       keyboard (`requestFocusAndShowKeyboardIfNeeded`) and places the cursor, so both fail the same way. Its
       long-press selection also checks the Final pass.
     - **The results `LazyColumn`**: `ScrollableNode` extends `DragGestureNode`. A move below touch slop sets
       `verifyConsumptionInFinalPass`, and seeing it consumed in Final moves the node to `AwaitGesturePickup`. That
       state re-arms only on a change that is still unconsumed in Final, which cannot happen under this root. The list
       scrolls only when the first MOVE after the down is already past slop in one step.
   - `ModalOverlay.kt:103-105` and the L13-2 plan (step 2) name this trap. They require items inside a `modalOverlay`
     to use `overlayItem` for exactly this reason. These items were not converted. A text field and a scrollable
     cannot be converted.
   - Failure scenario on a phone: tap New and type "s" (50 results, more than fit above the keyboard). Drag the list up:
     it does not move. Tap a city with a finger that drifts a pixel before lifting: nothing is added. After Back hides
     the keyboard, a tap on the field that moves at all does not bring it back.
   - This breaks the rule "no regression in the Clock's search".
   - The QA cannot see it. `adb input tap` sends DOWN and UP with no MOVE. `l13_13_row.sh` never picks a result,
     taps the field or scrolls. The existing search rows (e8, e31, edge_world, e10) pick results with `tap_node`, and
     none of them was re-run on bd114d21.
   - Remedy (root cause at the producer, within scope): the defect was only that the page's blank parts are not a hit
     target. Compose stops hit-testing lower siblings once a sibling's subtree is hit. So a pointer node on the
     search root that consumes nothing (or only its own down) keeps a hold from reaching the city list, and leaves
     the field, rows and list their gestures.
     - That form also keeps a horizontal drag on the search swiping the tabs, as it did before the fix.
     - Blocking that swipe is a behaviour change outside L13-13's defect. If it is wanted, it should be its own ruling.
     - Add a driver step with a finger-like tap (for example `input swipe x y x+3 y+3 150` on a result must add it)
       and a scroll of the results.

## Notes

1. **The LaunchedEffect keys are sound for one finger.**
   - They cannot close a menu the user has just opened: it cannot open while a keyed flag is already true (Select
     rows have no hold, AlarmTab.kt:176 and TimerTab's `pointerInput(select, checked)`; the expanded bar's scrim covers
     the page; the search is now modal). The one exception is World Clock in compare mode, where no key can change
     afterwards: the strip replaces the bar, and ‹ › write only `compareOffset`.
   - No bar action is missed. Add and About are page changes, which dispose the tab. Timer's Pin opens a system
     dialog, and the menu is visible again after it. A tab tap or swipe runs `leaveTabModes` and disposes the tab.
   - A key that goes true and back to false within one frame leaves the menu open, but visible. That is harmless.
2. **Two fingers can still hide a menu.**
   - Hold a city with one finger. Before `Edit.HOLD_MS` ends, tap New with another.
   - The search opens first, then the hold fires (`CityRow`'s `pointerInput` is keyed on `id` only,
     WorldClockTab.kt:196). `menuZone` is then set while `worldSearch` is already true, and no key changes, so the
     hidden menu and the invisible Back return.
   - AlarmRow is immune to this for Select, because its `pointerInput(select, …)` restarts.
   - A state rule instead of a transition closes this. For example, gate `onHold`, or the layer's `active` and its
     BackHandler, on `!nav.worldSearch && !nav.compare && !nav.barExpanded`. It is not blocking, since it needs two
     fingers.
3. **The effect's close is a plain write, one frame late.**
   - The hold-menu layer stays placed for about a frame after the bar action.
   - After New or "…", what opened is above that layer (the search page, the bar's scrim), so nothing is lost.
   - After Compare or Select, a down in that frame on the list lands on the stale scrim. This is L13-3's class at
     below one frame, so it is not blocking.
4. **Other "hidden under" candidates in the Clock: none with this shape.**
   - Compare tapped while the search is open (ClockTabs.kt:135): compare turns on under the search, but Back closes
     the search first. That is top-first order, and it existed before the fix.
   - The alarm editor's three flyouts under "…": they stay open and visible under the bar's transparent scrim. Back
     closes the flyout before the bar, which is L13-12 review note 5(a)'s order. The tabs now light-dismiss on "…"
     and the editor does not. That could be a follow-up, but it is not this row.
5. **Scope of the alarm and timer effects.** Those tabs have no page that can cover a hold menu, because Add is a page
   change. Their effects fix the reversed Back order for "…" and Select, which has the same root cause the L13-11/12
   review named (hold menus do not light-dismiss on bar use), so they are in scope. Only World Clock is driven (case 3),
   so the alarm and timer effects rest on this code reading alone.
6. **Comment nit.** WorldClockTab.kt:130 says "the compare strip". What closes the menu is the Compare button; using
   the strip's ‹ › does not.
