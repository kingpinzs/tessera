## 3. Findings

### R3F-01 · MAJOR · phase: the helper's (3 or 4, split decides) · The helper's (re)start path depends on Wi-Fi, a trusted network and a Global setting the shell cannot write without a one-time `pm grant`; Q13's "no manual steps after reboot" has a concrete route, and the helper's edge cases are not in the N-01 list
- Claim (unverified; QA on phone, all of it): (a) AOSP's `AdbDebuggingManager` turns Wireless debugging OFF (`Settings.Global.adb_wifi_enabled` → 0) whenever Wi-Fi is disabled or the Wi-Fi network disconnects, and refuses to enable it when not connected to Wi-Fi; on a network it has not seen before it asks for confirmation. (b) The TLS port is random per enable and must be discovered on-device (mDNS `_adb-tls-connect._tcp` via `NsdManager`). (c) Keys unused for 7 days are revoked unless Developer options "Disable adb authorization timeout" is on. (d) Once started and daemonised, the helper survives Wireless debugging being turned off (this is how Shizuku behaves), but every restart (reboot, crash, APK reinstall during dev) needs (a)-(c) satisfied again. Consequences: the only "no manual steps" route is: `adb shell pm grant <pkg> android.permission.WRITE_SECURE_SETTINGS` once at install (the permission carries the `development` flag, so `pm grant` works; same adb channel RV1 already uses) → on `BOOT_COMPLETED` wait for a trusted Wi-Fi network → set `adb_wifi_enabled=1` → discover the port → TLS-connect with the key pair paired once → `app_process` the helper. Two holes remain: reboot with Wi-Fi off (one of the four toggles the helper serves is Wi-Fi itself), and first boot on an unknown network. So "helper running" is a first-class state the action center and Cortana must reflect, and the edge-case set for this part is: reboot on trusted Wi-Fi / reboot with Wi-Fi off / reboot on an unknown network / Wireless debugging toggled off by the user / adb key revoked after 7 days / APK reinstalled while the helper runs (stale classpath) / helper killed by Device care. None of these is in r2-triage.md:11, which lists processes by type (listener, assistant, accessibility, IME, glance, LLM) and predates Q13.
- Evidence: PLAN.md:122-126 "started over Wireless debugging … that phase must look for a way to restart the helper after reboot with no manual steps before settling for a one-tap restart"; PLAN.md:149 "Install via adb (USB or Wireless debugging)" (the "or" is now stale for the helper: pairing over Wireless debugging is required even when the install goes over USB); r2-reuse-check.md:113 "must be re-started after every reboot"; r2-triage.md:11 (no helper row); PLAN.md:59 "each phase adds its own permission and liveness rows".
- Fix at the phase interview (no pre-split change): add the helper's edge-case set and the precondition rows (Developer options on, Wireless debugging paired, adb authorization timeout disabled, WRITE_SECURE_SETTINGS granted, helper running) to that phase; correct RV1's "or" to "USB or Wireless debugging for install; Wireless debugging pairing required for the helper".
- Owner question (at that phase interview, it is behaviour): when the helper is not running (e.g. reboot with Wi-Fi off), does the Wi-Fi tile open Android's Wi-Fi panel (a visible seam, against P2) or show "helper not running, tap to start" and do nothing else? Default if unasked: the second (no silent fallback, mirrors Q13's wording).

### R3F-08 · MINOR · phases 4, 5, 7 · RV10's "screen width = the shell window's bounds width" is right for the activity and wrong for a non-fullscreen overlay or the IME window
- Claim: RV10 defines px/epx from `WindowMetrics` of "the shell window". An overlay added with `WindowManager.addView` at `WRAP_CONTENT` (volume flyout) or the IME window reports its own bounds, not the display's, so an implementer following RV10 literally derives a different px/epx there. The rule should name the display's portrait bounds (`WindowManager.maximumWindowMetrics`, or the activity's `currentWindowMetrics` cached once) for every owned window. Same rule also yields 2 px/epx at Samsung's HD+ (720x1560) resolution option, which RV10 does not list; harmless, but the phase 1 `wm size` QA row could include it.
- Evidence: PLAN.md:162-163 "'Screen width' = the shell window's bounds width (WindowMetrics), giving 3 px/epx at FHD+ and 4 at QHD+."; PLAN.md:161 "Every window the shell owns (activity, overlays, IME, dialogs, popups) sets Density(pxPerEpx, fontScale = 1)."
- No owner question.
